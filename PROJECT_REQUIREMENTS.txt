--------------------------------------------------------------------------------
1. PRODUCT OVERVIEW
--------------------------------------------------------------------------------
- Shared hub for FinProms content: social media posts, reels, etc.
- Users subscribe, receive credits, spend credits on posts/reels, then download.
- Same codebase is reused for white-labelled hubs (multi-tenant style).
- Branding (colours, logo, etc.) must come from the database so each hub
  can look different without code changes.


--------------------------------------------------------------------------------
2. SHARED HUB — STEP 1 CORE FEATURES
--------------------------------------------------------------------------------

2.1 Content classification (THREE separate fields)
- TYPE — what the item is: post, reel, etc. (managed list; drives reel play button).
- CATEGORY — topical/grouping category (separate from type; e.g. product themes).
- TAGS — free labels for filtering (separate from type and category).
- Every content item has type + category + tags. Do NOT treat category as type.

2.2 Content browsing & listing UX
- Hub catalog / main member pages require login. Unauthenticated visitors are
  sent to the login screen and must not see the hub main/catalog UI.
- Users browse posts, reels, and other types.
- Listing page uses a 3-column grid (2 columns on tablet, 1 on mobile).
- For REELS: admin can upload a video when type is Reel.
- Reel video autoplays (muted, looping) on listing and detail pages.
- A play/pause “Reel” control sits at the top of the video to mark it as a reel
  and let the viewer pause/resume.
- Reels without a video still show the legacy centered play indicator on listing.
- "NEW" banner on new posts/reels:
  - Shown when the item is still within the "new" window.
  - Duration (e.g. number of days) is taken from the DATABASE (configurable
    setting), not hard-coded.

2.3 Content metrics
- Each post/reel tracks:
  - reach — unique impression when a user scrolls the listing and the post
    enters their viewport (POST /api/posts/reach with post_ids)
  - views — when a user opens the post detail page (GET /api/posts/{id})
  - buy count — when a user purchases the post
- Metrics are stored and shown on listing/detail for members according to their
  active subscription plan’s visibility flags (Power Admin / hub-admin can
  configure these on each plan):
  - Basic (default): reach only
  - Standard (default): reach + views
  - Premium (default): reach + views + buys
- Hub admins, Power Admin, and unlimited-credit advisors see all three metrics.
- Non-subscribers do not see metric counts.
- Plan fields: show_reach, show_views, show_buys (editable via subscription plan
  CRUD under Power Admin and hub-admin when dashboard_manage_plans is enabled).
- API responses include visible_metrics so the frontend knows what to render.

2.4 Subscriptions & Credits
- Users subscribe and receive credits.
- Credits are spent when buying posts/reels or post bundles.
- After purchase, users can download the content.

2.4a Post bundles
- Capability-gated (Capabilities matrix: dashboard_manage_bundles) — roles that
  Power Admin enables can create/edit bundles in the hub-admin dashboard.
- A bundle has a title, description, and total credits_cost (bundle price).
- Creators can include existing posts/reels and/or create new posts/reels and
  attach them in the same flow.
- Members browse bundles with the catalog; purchasing a bundle spends the
  bundle’s total credits and unlocks every post in the bundle.
- Invoices are generated for bundle purchases (type bundle_purchase).

2.5 One-off / Non-subscriber Purchases
- Users who are NOT subscribed can still buy individual posts/reels.
- Pricing rule: 1 credit = 1 pound (£1).

2.6 Invoices
- Invoices are generated for:
  a) Subscriptions
  b) Individual post/reel purchases

2.7 Roles & separate dashboards
There is ONE universal dashboard shell at /my-dashboard for every role.
What each user sees (sidebar + home cards) is driven by the Capabilities
matrix (and Power Admin’s own pa_* checklist for platform tools).

The member catalog (posts / bundles / plans) stays on the main website.
Staff and members open Dashboard from the main site nav; login lands on
/my-dashboard. Legacy /client-admin and /power-admin URLs redirect into
/my-dashboard. Members never see tools that are not enabled for their role.

ROLES (canonical list):

  1) POWER ADMIN (power_admin) — platform developers / us
     - Shared hub Power Admin control plane.
     - Manages hubs, hub Functionalities checklist (section 5.1),
       user capabilities matrix (section 5.2), payment methods, and Power Admin's
       OWN capability checklist (section 5.3).
     - What a power_admin can do on that control plane is gated by the separate
       Power Admin capabilities checklist (not the per-hub member/dashboard lists).

  2) FINPROMS ADMIN (finproms_admin) — shared hub admin
     - Day-to-day operator of the SHARED hub.
     - Manages shared hub content, types, categories, tags, plans, settings, etc.
     - Can generate AI posts and push/select content for white-labelled hubs
       (when those dashboard capabilities are enabled).
     - Uses the hub-admin shell; capabilities come from the SHARED hub's
       dashboard checklist (section 5.2).

  3) CLIENT ADMIN (client_admin) — white-labelled hub admin
     - Operator of ONE white-labelled hub.
     - Restricted vs FinProms admin; only tools Power Admin enables for that hub.
     - Uses the same hub-admin shell; capabilities from THAT hub's dashboard checklist.

  4) MANAGER (manager) — hub staff (shared or white-label)
     - Mid-level operational role (e.g. content/ops management without full
       client_admin rights). Exact screens TBD; gated by hub dashboard checklist
       and/or future manager-specific flags.

  5) APPROVER (approver) — compliance / review
     - Reviews/approves content (ties to compliance check flow, section 3.3).
     - Not a full hub admin by default; approval UI to be built later.

  6) ADVISOR (advisor) — reserved role label in the capabilities matrix
     - Not assigned automatically on plan subscribe or Excel import.
     - White-label invited advisors keep role=user; Excel import sets
       is_advisor and has_unlimited_credits when hub behaviour allows.
     - Uses member UI (same as user).

  7) USER (user) — general user / subscriber
     - Browse / subscribe / buy / download as user capability checklist allows.
     - Role stays user after a paid public-hub plan subscription (credits only).
     - Private-hub Excel-imported advisors also keep role=user (flags distinguish them).
     - Label in the Capabilities matrix is "User" (not "Member").

Notes:
- Former "admin" → client_admin. Shared hub operator should use finproms_admin
  going forward (existing client_admin on shared may be migrated).
- Seeded shared-hub FinProms admin: finproms@hubfinproms.com (role=finproms_admin).
- Advisor import keeps role=user and sets is_advisor / unlimited flags.
- Public plan subscribe does NOT change role (stays user; credits only).
- Role alone does not unlock every screen — Power Admin checklists still gate
  member UI, hub-admin UI, and power_admin UI.

4. WHITE-LABELLED HUBS
--------------------------------------------------------------------------------

4.1 Multi-instance / Same Codebase + Separate Databases
- The shared hub is copied/reused to form white-labelled hubs.
- There will be MANY white-labelled hubs.
- Code must remain the SAME for shared hub and all white-labelled hubs.
- Each hub (shared AND every white-label) has its OWN database — not a shared
  multi-tenant DB. Content, users, and settings for a white-label live in that
  hub's database only.
- Everything that differs per hub (especially branding) must be driven by DB:
  - Application name
  - Colour scheme (primary / secondary)
  - Logo
  - Other tenant-specific settings as needed
- Hub admins with `dashboard_manage_settings` can edit these branding fields
  (plus NEW banner days) for the current hub via client-admin settings; they
  are returned on public GET /hub under branding and applied in the UI.
- Power Admin on the SHARED hub is the control plane. The shared DB stores a
  hub registry for every white-label, including deploy wiring so shared can
  reach that hub for management / content push:
  - frontend_url — public site URL for that hub's deploy
  - api_url — optional backend API base URL
  - db_* — that white-label's database connection (host, port, database,
    username, encrypted password, driver) so shared can push content / sync
  - deploy_notes — free-text ops notes
  - Deploy contract: white-label deploy uses the SAME codebase with its OWN
    .env (its own DB_* + FRONTEND_URL / APP_URL). HUB_SLUG identifies the hub
    on that deploy. Shared does NOT share the white-label database.
  - When frontend_url is set, emails / Stripe return URLs prefer that hub URL
    over the global FRONTEND_URL env (on that hub's own deploy).
  - Power Admin hub detail shows a deploy checklist + copyable env snippet.
    Registry "ready" = active + frontend_url + remote DB credentials set.
  - Hub list badges: Wiring ready / Needs wiring.
- Content push (shared → white-label): FinProms admin selects posts and target
  hub(s); shared uses the stored remote DB connection (or API) to publish into
  that white-label's own database. (Feature still to build.)

4.2 Private Access (White-labelled)
- White-labelled hubs are PRIVATE.
- Public users cannot subscribe.
- Client provides an Excel sheet of advisors.
- Advisors from that sheet are added into the application.
- Power Admin sets subscriber credits for the hub (dashboard + Capabilities):
  - Capability: `dashboard_manage_subscriber_credits` (private-hub dashboard tool)
  - Unlimited (default for white-label), OR
  - A fixed number of credits per subscriber per billing period.
- On Excel import, each new / reactivated advisor receives that allotment
  (unlimited flag, or balance set to the hub credit number).
- If Power Admin changes the credit number (or switches unlimited ↔ fixed)
  after advisors are already subscribed, existing balances are NOT changed
  mid-period; the new allotment is applied on the next monthly autorenew
  to all active advisors.
- Client admin (or Power Admin with import capability) can Discontinue an
  individual advisor: permanent end of access (WP FPSUB end equivalent).
  Discontinued advisors cannot log in, drop out of billing counts, and are
  not restored when the hub flips private again. Re-importing the same email
  restores them. Gated by Capabilities matrix key `advisor_discontinue`.
- When Power Admin switches a hub from private → public (Functionalities):
  - All Excel-imported advisors are SUSPENDED (not deleted): cannot log in,
    lose unlimited/subscription access, excluded from advisor billing counts.
  - Advisor Stripe auto-renew is canceled; pending advisor billings are canceled.
  - Private-related functionalities are turned off and public ones turned on
    (paid credits, one-off purchase, public subscribe; unlimited credits and
    advisor subscriber billing off).
- When the hub is switched back public → private:
  - Previously suspended imported advisors are REACTIVATED with the hub’s
    current subscriber-credit allotment and advisor_import subscriptions restored.
  - Auto-renew is NOT restarted automatically; client admin pays again after
    import / billing flow if needed.

4.3 Pricing Tiers for White-labelled (Managed by Shared Hub)
- Pricing depends on number of subscribers (advisors), e.g.:
  - 0–99 subscribers → £25 / advisor / month
  - 100–249 subscribers → £22
  - 250–499 subscribers → £20
  - 500+ subscribers → £15
  - (Defaults copied from WordPress FP Subscriptions plugin; Power Admin can edit)
- Import billing (WP-style): tier RATE is taken from TOTAL active advisors;
  the invoice charges RATE × THIS IMPORT BATCH only (already-paid advisors
  are not recharged). Example: 99 imported → £25×99; later +249 (total 348)
  → £20×249 only.
- Monthly auto-renew: ONE invoice for all active advisors =
  rate(total) × total (single Stripe subscription per hub).
- Shared hub manages these pricing rules.

4.4 Content for white-labelled hubs (from shared control plane)
- Capability: `dashboard_push_content` — “Publish content to white-labelled hubs”.
- On Posts / Types / Categories / Tags / Bundles, users with this capability see a
  Hub dropdown (same UI pattern as Capabilities / Functionalities).
- Selecting the shared hub → manage the shared catalog as usual.
- Selecting a white-label hub → create/list content in THAT hub’s OWN database
  only. Those posts/reels are NOT stored on the shared hub and do not appear in
  the shared catalog.
- Target white-label must have Functionalities `receive_content_from_shared`
  and remote DB credentials configured.
- Media for white-label posts is stored as a public URL reachable from shared
  storage (file is uploaded via shared, path saved on the white-label DB).

4.5 Code Updates
- Updates made in the shared hub codebase are also reflected in white-labelled
  hubs (same codebase / deploy model).

5. RIGHTS / PERMISSIONS CHECKLISTS (CRITICAL)
--------------------------------------------------------------------------------
- Because shared and white-labelled use the SAME code, behaviour differences
  must be gated by checklists (feature flags / rights), not hard-coded forks.
- Power Admin manages these checklists from the SHARED hub Power Admin
  dashboard, for the shared hub AND for EACH white-labelled hub.
- Opposite options (e.g. public vs private, paid vs unlimited credits) must be
  mutually exclusive: checking one auto-unchecks the other.

5.1 Hub Functionalities checklist (Power Admin → Functionalities)
- Formerly "hub behaviour". Controls how the hub works for that tenant, e.g.:
  - Public subscribe / self-registration vs private invite-only
  - Paid credits vs unlimited credits
  - One-off purchase for non-subscribers
  - Receive content from shared hub
  - Future: compliance
- Each hub (shared + each white-label) has its own configuration.
- Edited ONLY from Hub Functionalities / hub checklist screens — not from the
  Capabilities matrix (no duplication).

5.2 User capabilities matrix (REQUIRED — Power Admin → Capabilities)
- Power Admin manages what users can do from their dashboards / member UI,
  for BOTH shared hub and white-labelled hubs — by ROLE (matrix).
- Distinct from Functionalities (5.1). Do NOT repeat Functionalities here.
- This is a role × capability matrix per hub, managed only from the
  shared hub Power Admin dashboard. Examples of what it should control:

  Member-facing (end users / advisors / staff columns):
  - Browse catalog / posts / reels — available for ALL roles in the matrix
    (Power Admin, FinProms admin, client admin, manager, approver, advisor, user)
  - View plans / self-serve subscribe
  - One-off purchase / spend credits
  - Download purchased content
  - In-app post editing (when built)
  - Other member features as they are added

  General options (dashboard) — member personal dashboard sections, ALL roles:
  - Show subscription (active plan + recent subscriptions)
  - Show remaining credits
  - Show invoices (summary on /my-dashboard)
  - Show purchases (summary on /my-dashboard)
  - Members with any of these enabled see Dashboard in the member nav and can
    open /my-dashboard (role=user lands here after login when enabled)

  Hub-admin dashboard (FinProms admin on shared; client_admin on white-label):
  - Manage posts/reels — enableable for ALL roles in the matrix
    (Power Admin, FinProms admin, client admin, manager, approver, advisor, user);
    remaining roles (approver / advisor / user) default OFF until Power Admin enables them
  - Manage post bundles (group posts/reels; description + total credits) — same roles
  - Manage types / categories / tags — same roles
  - Manage subscription plans — same roles
  - Manage settings (NEW banner, logo upload, color scheme, application name) — same roles
  - Confirm bank transfers — same roles
  - Import advisors (Excel/CSV) — same roles
  - Discontinue advisors — separate capability; who can permanently end an
    imported advisor’s access — same roles
  - View activity logs / report — who can open the audit trail and activity
    report for the hub — same roles
  - AI content generation / push content to white-labels — same roles
    (typically FinProms admin / shared-only where appropriate)
  - Any other admin dashboard screens/actions
  - Approver / advisor / user only see the hub-admin shell when at least one
    dashboard capability is enabled for their role on that hub

- White-label client_admin sees ONLY the dashboard items Power Admin enables
  for that hub (restricted options).
- FinProms admin on shared hub sees the shared-hub set of capabilities Power
  Admin enables (typically broader, including AI / distribute to white-labels).
- Do NOT hard-code "if shared show X else hide Y" in many places — use the
  checklist so Power Admin can change it without code deploys.

5.3 Power Admin capabilities checklist (SEPARATE — platform level)
- Distinct from per-hub Functionalities (5.1) and user capabilities (5.2).
- Controls what power_admin users can do on the Power Admin control plane
  (shared hub /power-admin), for example:
  - View platform dashboard
  - Manage hubs (create/list/edit white-label hubs)
  - Manage hub Functionalities checklists
  - Manage payment methods
  - Manage Power Admin / user capabilities matrix (this list + 5.2)
  - Manage users / roles (create, update, delete, assign roles)
- Stored as platform settings (not per-hub).
- Edited from Power Admin → Capabilities (Power Admin column).
- Power Admin nav/actions and APIs must respect these flags.

--------------------------------------------------------------------------------
- Role: power_admin (platform developers / us).
- Dashboard is SEPARATE from the member app, FinProms admin, and white-label
  client_admin (own shell/routes, e.g. /power-admin).
- Power Admin logs into the SHARED hub and from there manages:
  1) Hub registry (create/list white-labelled hubs, branding basics)
  2) Hub Functionalities checklist per hub (section 5.1) — how the hub works
  3) User capabilities matrix per hub (section 5.2) — what members and hub
     admins can do on shared AND each white-labelled hub (by role)
  4) Power Admin's OWN capabilities (section 5.3) — same Capabilities screen
  5) Platform payment methods (Stripe / bank transfer), and other platform
     settings as needed
- Functionalities and Capabilities must NOT duplicate each other in the UI.
- This is the central control plane for ALL tenant behaviour and UI capabilities.
- Power Admin does NOT replace FinProms admin day-to-day content work; they
  configure rights so FinProms admin and client_admins operate within bounds.


--------------------------------------------------------------------------------
6A. ACTIVITY LOGS & ACTIVITY REPORT
--------------------------------------------------------------------------------
- Every meaningful user activity is recorded in an activity_logs audit trail
  (per hub), including:
  - Auth: register, login, logout, failed login, blocked login (suspended /
    discontinued / invite-only)
  - Successful mutating API actions (POST / PUT / PATCH / DELETE): content,
    plans, settings, advisor import/discontinue, billing, capabilities, hubs,
    purchases, subscriptions, etc.
- Sensitive fields (passwords, secrets, card data) are NEVER stored; payloads
  are redacted / truncated.
- Activity report (aggregates): totals, unique users/actions, counts by action,
  by user, and by day — filterable by user, action, date range, and text search.
- WHO CAN SEE the logs and report is gated by Capabilities matrix key
  `dashboard_view_activity_logs` (hub-admin dashboard group). Applicable roles:
  finproms_admin, client_admin, manager, and power_admin (when enabled for that
  hub). Power Admin toggles this per hub / role on the Capabilities screen.
- APIs (hub_can:dashboard_view_activity_logs):
  - GET /api/client-admin/activity-logs (+ /power-admin/…) — paginated feed
  - GET /api/client-admin/activity-logs/report (+ /power-admin/…) — aggregates
- Frontend: Activity logs page under hub-admin and Power Admin shells, shown
  only when the viewer’s role has the capability.
