--------------------------------------------------------------------------------
1. PRODUCT OVERVIEW
--------------------------------------------------------------------------------
- FinProms content platform: social media posts, reels, etc.
- Users subscribe, receive credits, spend credits on posts/reels, then download.
- Branding (colours, logo, etc.) must come from the database so each hub
  can look different without code changes.

THREE HUB TYPES (same codebase, separate deploys / databases):

  A) CENTRAL HUB CONTROLLER ("Central Hub")
     - Platform control plane ONLY — not a member content catalog for end users.
     - Where Power Admin remotely controls ALL hubs (Shared + White-labelled).
     - Where new Shared hubs and White-labelled hubs are registered, wired, and
       spawned (copy same codebase onto another cPanel / hosting instance).
     - Owns the hub registry, remote DB credentials, Functionalities / Modules /
       Capabilities for every hub, platform payment methods, and Power Admin tools.
     - Does NOT replace day-to-day content work on Shared or White-label hubs.

  B) SHARED HUB
     - A normal content hub for FinProms public/shared catalog (posts, reels,
       plans, subscriptions, purchases).
     - Operated day-to-day by FinProms admin (and staff roles as enabled).
     - Is NOT the control plane. It is controlled remotely by Central Hub
       (same remote-control pattern as white-labelled hubs).
     - May still receive content / configuration push FROM Central Hub when
       those features are enabled.
     - Additional Shared hubs can be created the same way as white-labels:
       copy codebase to another cPanel, own DB + .env, register on Central Hub.

  C) WHITE-LABELLED HUB
     - Private client hub (advisor Excel import, restricted options).
     - Same codebase; own database; branding from DB.
     - Controlled remotely by Central Hub (hub switcher / acting hub / remote DB).

Deploy rule:
- ONE codebase for Central Hub Controller + Shared Hub(s) + all White-labelled hubs.
- Each instance has its OWN database and .env (HUB_SLUG, DB_*, FRONTEND_URL / APP_URL).
- Central Hub is the master registry and remote-control source — not Shared Hub.


--------------------------------------------------------------------------------
1A. CENTRAL HUB CONTROLLER (CONTROL PLANE)
--------------------------------------------------------------------------------
- Purpose: separate remote control from content hubs so Shared Hub no longer
  controls itself and other hubs from the same place.
- Power Admin logs into Central Hub and from there:
  1) Hub registry — create / list / edit Shared hubs AND White-labelled hubs
  2) Deploy wiring per hub — frontend_url, api_url, db_* (encrypted password),
     deploy_notes, copyable env snippet / checklist
  3) Hub Functionalities + Modules checklists per hub (section 5.1 / 5.1A)
  4) User capabilities matrix per hub (section 5.2)
  5) Power Admin's OWN capabilities checklist (section 5.3)
  6) Platform payment methods and other platform settings
  7) Remote control / hub switcher — act on a Shared or White-label hub's own
     database (content, types, categories, tags, bundles, settings, etc.) when
     wiring + receive_content / remote-control flags allow
- Spawning a new hub (Shared or White-label):
  - Ops copies the SAME codebase to another cPanel (or hosting).
  - New instance gets its OWN DB + .env (HUB_SLUG, DB_*, URLs).
  - Power Admin registers that hub on Central Hub and stores deploy wiring /
    remote DB credentials so Central can reach it.
  - Hub type is set in registry (shared | white_label); packaging modules and
    default Functionalities follow that type.
- Central Hub DB stores the hub registry for EVERY Shared and White-label hub.
  Content catalogs for those hubs live in EACH hub's own database — Central
  does NOT share those databases.
- Registry "ready" = active + frontend_url + remote DB credentials set.
  Hub list badges: Wiring ready / Needs wiring.
- Central Hub itself is NOT a substitute Shared catalog; member browse/buy
  flows belong on Shared / White-label instances.


--------------------------------------------------------------------------------
2. SHARED HUB — STEP 1 CORE FEATURES
--------------------------------------------------------------------------------
(Shared Hub = content hub. Platform control lives on Central Hub Controller.)

2.1 Content classification (THREE separate fields)
- TYPE — what the item is: post, reel, etc. (managed list; drives reel play button).
- CATEGORY — topical/grouping category (separate from type; e.g. product themes).
- TAGS — free labels for filtering (separate from type and category).
- Every content item has type + category + tags. Do NOT treat category as type.

2.2 Content browsing & listing UX
- Hub catalog / main member pages require login. Unauthenticated visitors are
  sent to the login screen and must not see the hub main/catalog UI.
- Users browse posts, reels, and other types.
- Listing page uses a 3-column grid (2 columns on tablet, 1 on mobile).
- For REELS: admin can upload a video when type is Reel.
- Reel video autoplays (muted, looping) on listing and detail pages.
- A play/pause “Reel” control sits at the top of the video to mark it as a reel
  and let the viewer pause/resume.
- Reels without a video still show the legacy centered play indicator on listing.
- "NEW" banner on new posts/reels:
  - Shown when the item is still within the "new" window.
  - Duration (e.g. number of days) is taken from the DATABASE (configurable
    setting), not hard-coded.

2.2a Shared Hub self-registration email verification
- When public self-registration is enabled (`public_subscribe` / not invite-only),
  new members must verify their email before they can sign in.
- Register creates the account with `email_verified_at` null, does NOT issue a
  Sanctum token, and sends a hub-branded verification link
  (`{frontend}/verify-email?token=…&email=…`). Link expires in 60 minutes.
- Verify endpoint marks the email verified, sends the welcome email, and returns
  an auth token so the member is signed in.
- Unverified members are blocked at login with `email_verification_required` and
  may request a resend (throttled).
- Admin-created and Excel-imported users are marked verified immediately.
- Existing accounts are backfilled as verified by migration so they are not locked out.
- Email template catalog event: `email_verification` (editable like other templates).
- APIs: POST /api/auth/verify-email, POST /api/auth/resend-verification.
- Frontend: Register shows “check your email”; VerifyEmail page; Login offers resend.

2.2b Two-factor authentication (login OTP) — per user (all hub types)
- NOT a hub Functionalities checkbox. Each user opts in from Update profile
  (`users.two_factor_enabled`, default OFF). Only that user gets email OTP
  after a successful password check on every sign-in.
- Enabling / disabling 2FA (and changing email) requires `current_password`.
- Login returns `otp_required` + `otp_challenge` (no Sanctum token yet)
  only when that user has 2FA enabled.
  A 6-digit code is emailed (hub From address / MAIL_FROM fallback).
  Code expires in 10 minutes; max 5 failed attempts; resend throttled 60s.
- APIs: POST /api/auth/verify-login-otp, POST /api/auth/resend-login-otp.
- Public GET /hub exposes `auth.login_otp_per_user` (true) and
  `auth.login_otp_required` (always false; legacy clients).
- Email template catalog event: `login_otp` (always available to edit).
- Frontend Login shows a second step when the login response has otp_required.
- Profile page (all authenticated users): Update profile — name, email,
  avatar (profile picture), and two-factor toggle.
  API: PUT/PATCH/POST /api/auth/profile (POST for multipart avatar).
  Changing email clears verification and sends a new verification link.
  Avatar stored on public disk (`avatars/{user_id}/…`); URL via /api/media/.

2.2c Terms & Conditions (all hub types)
- Capability matrix key: `dashboard_manage_terms` (“Manage terms & conditions”)
  in Hub operations. Defaults ON for hub-admin style roles on Shared and
  White-label (and available on Central). Who may edit content is controlled
  per role on the Capabilities matrix.
- Hub stores rich HTML Terms & Conditions (`hubs.terms_and_conditions` JSON:
  content, version, updated_at). Each hub type seeds relevant default copy
  (Shared catalogue / White-label private firm / Central control plane) which
  capable users can edit via a rich-text editor.
- On first login (and when the version changes after an edit), authenticated
  users must view and accept the current terms before using the app.
  Acceptance is stored on the user: `terms_accepted_at`, `terms_accepted_version`.
- APIs: GET/PUT /api/client-admin/terms, POST /api/client-admin/terms/reset
  (hub_can:dashboard_manage_terms); POST /api/auth/accept-terms (auth).
- Public GET /hub includes `auth.terms` { required, version, content }.
- Frontend: /my-dashboard/terms admin page; TermsGate modal after login.

2.3 Content metrics
- Each post/reel tracks:
  - reach — unique impression when a user scrolls the listing and the post
    enters their viewport (POST /api/posts/reach with post_ids)
  - views — when a user opens the post detail page (GET /api/posts/{id})
  - buy count — when a user purchases the post
- Metrics are stored and shown on listing/detail for members according to their
  active subscription plan’s visibility flags (Power Admin / hub-admin can
  configure these on each plan):
  - Basic (default): reach only
  - Standard (default): reach + views
  - Premium (default): reach + views + buys
- Hub admins, Power Admin (when acting on that hub), and unlimited-credit
  advisors see all three metrics.
- Non-subscribers do not see metric counts.
- Plan fields: show_reach, show_views, show_buys (editable via subscription plan
  CRUD under Power Admin and hub-admin when dashboard_manage_plans is enabled).
- API responses include visible_metrics so the frontend knows what to render.

2.4 Subscriptions & Credits
- Users subscribe and receive credits.
- Credits are spent when buying posts/reels or post bundles.
- After purchase, users can preview the content in-app (no file download).

2.4a Post bundles
- Capability-gated (Capabilities matrix: dashboard_manage_bundles) — roles that
  Power Admin enables can create/edit bundles in the hub-admin dashboard.
- Website visibility is gated separately by `member_browse_bundles` (Member
  catalog group on the Capabilities matrix). When off for a role, Bundles nav
  and /bundles pages are hidden for that role; turn off for every role to hide
  bundles for the whole hub. Defaults ON for Shared / White-label, OFF on Central.
- A bundle has a title, description, and total credits_cost (bundle price).
- Creators can include existing posts/reels and/or create new posts/reels and
  attach them in the same flow.
- Members browse bundles when `member_browse_bundles` is on; purchasing a
  bundle spends the bundle’s total credits and unlocks every post in the bundle.
- Invoices are generated for bundle purchases (type bundle_purchase).

2.5 One-off / Non-subscriber Purchases
- Users who are NOT subscribed can still buy individual posts/reels.
- Pricing rule: content is priced in credits (no pound display in catalog copy).

2.6 Invoices
- Invoices are generated for:
  a) Subscriptions
  b) Individual post/reel purchases

2.7 Roles & separate dashboards
There is ONE universal dashboard shell at /my-dashboard for every role.
What each user sees (sidebar + home cards) is driven by the Capabilities
matrix (and Power Admin’s own pa_* checklist for platform tools on Central Hub).

The member catalog (posts / bundles / plans) stays on the main website of
Shared / White-label hubs by default. Central may optionally expose a public
site shell when Power Admin enables member_* caps on Central’s own matrix.
Staff and members open Dashboard from the main site nav; login lands on
/my-dashboard. Legacy /client-admin and /power-admin URLs redirect into
/my-dashboard. Members never see tools that are not enabled for their role.

ROLES (canonical list):

  1) POWER ADMIN (power_admin) — platform developers / us
     - Logs into CENTRAL HUB CONTROLLER (control plane).
     - Manages hubs (Shared + White-label), hub Functionalities + Modules
       checklist (section 5.1 / 5.1A), user capabilities matrix (section 5.2),
       payment methods, and Power Admin's OWN capability checklist (section 5.3).
     - Remotely controls Shared and White-labelled hubs (hub switcher / acting
       hub) when those capabilities and wiring allow.
     - What a power_admin can do on that control plane is gated by the separate
       Power Admin capabilities checklist (not the per-hub member/dashboard lists).

  2) FINPROMS ADMIN (finproms_admin) — Shared hub admin
     - Day-to-day operator of a SHARED hub (content hub).
     - Manages that Shared hub’s content, types, categories, tags, plans,
       settings, etc.
     - Can generate AI posts (when built) and may control white-labelled hubs
       via Central Hub remote tools ONLY if Power Admin enables that capability
       for their role — Preferred path is Power Admin on Central Hub for
       cross-hub control; FinProms admin focus is Shared hub day-to-day ops.
     - Uses the hub-admin shell; capabilities come from THAT Shared hub's
       dashboard checklist (section 5.2), managed on Central Hub.

  3) CLIENT ADMIN (client_admin) — white-labelled hub admin
     - Operator of ONE white-labelled hub.
     - Restricted vs FinProms admin; only tools Power Admin enables for that hub.
     - Uses the same hub-admin shell; capabilities from THAT hub's dashboard checklist.

  4) MANAGER (manager) — hub staff (Shared or White-label)
     - Mid-level operational role (e.g. content/ops management without full
       client_admin rights). Exact screens TBD; gated by hub dashboard checklist
       and/or future manager-specific flags.

  5) APPROVER (approver) — compliance / review
     - Reviews/approves content (ties to compliance check flow, section 3.3).
     - Not a full hub admin by default; approval UI to be built later.

  6) ADVISOR (advisor) — reserved role label in the capabilities matrix
     - Not assigned automatically on plan subscribe or Excel import.
     - White-label invited advisors keep role=user; Excel import sets
       is_advisor and has_unlimited_credits when hub behaviour allows.
     - Uses member UI (same as user).

  7) USER (user) — general user / subscriber
     - Browse / subscribe / buy / download as user capability checklist allows.
     - Role stays user after a paid public-hub plan subscription (credits only).
     - Private-hub Excel-imported advisors also keep role=user (flags distinguish them).
     - Label in the Capabilities matrix is "User" (not "Member").

Notes:
- Former "admin" → client_admin. Shared hub operator should use finproms_admin
  going forward (existing client_admin on shared may be migrated).
- Seeded shared-hub FinProms admin: finproms@hubfinproms.com (role=finproms_admin).
- Advisor import keeps role=user and sets is_advisor / unlimited flags.
- Public plan subscribe does NOT change role (stays user; credits only).
- Role alone does not unlock every screen — Power Admin checklists (on Central
  Hub) still gate member UI, hub-admin UI, and power_admin UI.
- LEGACY NOTE: Older builds treated Shared Hub as the control plane. Target
  architecture moves the control plane to Central Hub Controller; Shared Hub
  becomes a controllable content hub only.

3. SHARED HUB — FUTURE FEATURES

3.1 AI Content Generation (later)
- Posts/reels added to the hub will also be generated by AI.
- FinProms admin (on Shared hub) generates AI content for white-labelled hubs
  (and/or via Central Hub remote tools when enabled).
- AI will be trained / configured for:
  - Types of posts and reels to generate
  - What text/copy should be added

3.2 In-app Post Editing (later)
- Users who buy a post can edit that post within the application.

3.3 Social Media Compliance
- After purchase (and later editing), posts can go through a compliance check.
- Power Admin (on Central Hub) enables the **Social Media Pre Approval Workflow**
  module per hub (Modules checklist). Website features are separate modules —
  see 3.3d (Website Template Library + Website Content Pre Approval Workflow).
- While the module is off, all Social Media Compliance capabilities appear
  blurred / inactive on the Capabilities matrix (same pattern as private/public).
- Who can submit, assign, review, view queues, or open reports is controlled
  only by the Capabilities matrix — not hard-coded to Approver / buyer roles.
- Buyers submit a purchased post (description + image); managers assign to
  reviewers; reviewers set Pending / Approved / Rejected / Approved with
  Feedback; version history supports reject-resubmit and approve-with-feedback
  confirm/reupload. Emails notify admins, assignees, and submitters.
- Optional **supporting files** (PDF, Office, images, ZIP; max 10 × 10 MB) may
  be attached on submit (advisor), review/approve-reject (approver), and
  change-status (manager), in addition to the required media attachment.
  Field: `supporting_files[]`. Copied across versions on resubmit /
  change-status when no new files are uploaded.
- **UI:** show supporting files inside each entry of **version history**
  (`versions[].supporting_files`) when any exist — never as a separate
  request-level supporting-files box. Each file includes `source`,
  `uploaded_by_name`, and `uploaded_by_role` (`advisor` | `approver` |
  `manager`) so the UI can label who attached it.
- All Social Media Compliance mutations and report/chart views are written to
  activity_logs (actions: smc.submit / assign / unassign / review / resubmit /
  confirm_feedback / change_status / reports.* / charts.*).
- Each request also gets a dedicated **compliance audit trail**
  (`compliance_audit_events`): submit / assign / unassign / review / resubmit /
  confirm_feedback / change_status, with actor **name, email, role**, optional
  related user (e.g. assignee), from→to status, version, and description.
  Detail (`includeVersions`) and reports expose `audit_trail[]` plus
  `audit_trail_summary` on CSV export; rows also include assigner name/email/role.

3.3b General Compliance
- Same review flow as Social Media Compliance (submit → assign → review →
  versions / reports), but submissions are free-form: required description
  textarea + optional multiple **attachments** (primary content files) and
  optional **supporting files** (evidence; PDF, Office, images, ZIP, etc.;
  max 10 × 10 MB each field).
- Attachments and supporting files are distinct: multipart fields
  `attachments[]` and `supporting_files[]` are stored and returned separately
  (`kind` on each file row). Do not alias one into the other.
- Supporting files may be attached by the advisor on submit/resubmit/confirm,
  by the approver on review, and by the manager on change-status (appended to
  the current/new version).
- **UI:** render supporting files only inside **version history**
  (`versions[].supporting_files`); primary `attachments` may still show with
  the request content. Do not show a separate supporting-files panel.
- Power Admin enables the **General Compliance** module per hub. Capabilities
  (`gc_*`) are blurred while the module is off.
- Activity logs use `gc.*` actions.
- Same **compliance audit trail** as SMC (`module=gc`) on every lifecycle event;
  reports and request detail include full history with actor name/email/role.

3.3e Support Tickets (error / bug reporting)
- Power Admin enables **Support Tickets** as a hub Functionalities flag
  (`support_tickets`) — NOT a Modules-page product module (the 6 product
  modules stay unchanged). Available on Shared, White-label, and Central Hub.
- Users with `st_submit_ticket` can report system errors:
  - Required: subject, module area (dropdown of product areas), description
  - Optional: category (bug / UI / performance / data / access / feature / other),
    priority (low / medium / high / critical), page URL, browser info,
    screenshots (`screenshots[]` — images or PDF, max 8 × 5 MB)
- Statuses: Open → In Progress → Waiting on User → Resolved → Closed
- Capabilities (`st_*`, blurred while Functionalities → Support Tickets is off):
  - `st_submit_ticket` — submit tickets
  - `st_view_own_tickets` — own ticket history & detail
  - `st_view_all_tickets` — full hub queue (developer inbox)
  - `st_change_ticket_status` — change status + resolution note
  - `st_comment_on_tickets` — add follow-up comments / screenshots
- APIs (also under `/api/client-admin/*` and `/api/power-admin/*` for queue):
  - GET /api/support-tickets/options
  - POST /api/support-tickets
  - GET /api/support-tickets/mine
  - GET /api/support-tickets/{id}
  - POST /api/support-tickets/{id}/comments
  - GET …/support-tickets (admin list)
  - POST …/support-tickets/{id}/change-status
- Activity logs: `st.submit` / `st.change_status` / `st.comment`
- Frontend: `/my-dashboard/support-tickets` (my / new / queue / detail)

3.3c Website Content Pre Approval supporting files
- Change requests accept optional supporting files on submit (advisor/editor),
  approve / reject / approve-with-feedback / schedule (approver), and
  change-status (manager) via `supporting_files[]` (same limits as other
  compliance modules). Stored per change-request version with uploader
  attribution (`source`, `uploaded_by_*`, `uploaded_by_role`).
- **UI:** show supporting files inside each version in version history only —
  never as a separate request-level supporting-files box.
- Change requests record a **compliance audit trail** (`module=wc`) for submit /
  assign / review / reject / schedule / publish / resubmit / confirm_feedback /
  change_status, with actor name/email/role. Detail responses include
  `audit_trail[]`. Platform report also has
  `GET .../website-compliance/reports/change-requests` for full history rows.

3.3d Website Template Library vs Website Content Pre Approval Workflow
- Formerly one combined “Website Compliance” product. They are now TWO Modules
  checklist items. Content Pre Approval depends on Template Library.
- API namespace remains `/api/website-compliance/*` (shared tables); module and
  capability gates decide which half is available.
- Frontend dashboard shows TWO nav sections (not one “Website Compliance”
  umbrella): Website Template Library and Website Content Pre Approval.

  A) Website Template Library (`module_website_template_library`)
     - Showcase website templates only — no content pre-approval queue here.
     - Power Admin (if `wc_manage_templates`) adds / edits / deletes templates.
       When registering / editing a template, Power Admin can attach one or more
       colour schemes (name + primary + secondary) that suit that template;
       stored on `wc_templates.color_schemes` (JSON).
       Power Admin also defines the **available pages** for that template
       (name + slug + optional description) on `wc_templates.available_pages`
       (JSON). Requesters later select which of those pages to include.
     - Capable users browse the template catalogue.
     - Capable users request a template by filling the deployment form
       (`wc_request_deployments`) — domain, branding, colours, etc.
       On the request form they pick one of the template’s colour schemes, or
       enter an optional custom primary / secondary if none of the offered
       schemes fit. Chosen colours are saved on the template request as usual
       (`primary_color` / `secondary_color`).
       The request form also collects optional website content extras stored on
       `wc_template_requests`:
         • `services` — name + attached document (PDF/Office) list
         • `images` — uploaded image URL + optional label list
         • `contact_details` — phone, email, address, website
         • `policies` — name + attached document (PDF/Office) list
         • `selected_pages` — slugs chosen from the template’s `available_pages`
         • `page_contents` — document attachment (`url` + `name`) keyed by selected page slug
           (typed textareas are not used; attach a file for each page/service/policy)
     - Optional staff path: request on behalf of / assign to an advisor
       (`wc_assign_website_templates`).
     - Power Admin (if `wc_deploy_websites`) manually deploys the pending
       request onto the respective cPanel (credentials + domain on deploy).
       Deploy is never automatic from the request form.
     - Related caps: `wc_view_all_deployments` (list), `wc_deploy_websites`
       (deploy / reject).
     - Capabilities in group “Website Template Library” are blurred while
       this module is off.

  B) Website Content Pre Approval Workflow (`module_website_compliance`)
     - Requires Website Template Library enabled (module dependency).
     - Full compliance flow on a deployed site’s sections.
     - Advisor / editor (if capable) locks/edits sections and submits change
       requests (`wc_edit_sections`, `wc_submit_change_requests`).
     - Approver / manager sees the whole flow: assign → review →
       approve & publish (status → published, immediate) OR approve only
       (status → approved, then schedule → scheduled → published) /
       reject / approve-with-feedback.
       Status overrides are blocked once published or scheduled.
       (`wc_assign_change_requests`, `wc_review_change_requests`,
       `wc_change_request_status`, `wc_view_all_change_requests`, …).
     - Optional bypass: publish live without review (`wc_publish_live_content`).
     - Supporting files: section 3.3c.
     - Capabilities in group “Website Content Pre Approval” are blurred while
       this module is off.

3.4 Firm Head of Firm & Firm Documents
- Firms already exist on hub databases (`firms` + `users.firm_id`; capability
  `dashboard_manage_firms`). This section adds Head of Firm allocation and a
  firm-scoped Documents library (attachments) with per-member rights.
- Applies on Shared and White-labelled hubs (each hub’s own firms / members).
  Backend and frontend both required.

3.4.0 Functionality gate (hub-wide matrix only)
- Hub Functionalities checklist flag: `firm_documents` (“Firm documents”).
  Default OFF. Power Admin enables it per hub on Functionalities (often from
  Central Hub Controller → Hub Functionalities for that hub).
- While OFF, firm-document Capabilities (view / add / delete / archive for ALL
  firms) are blurred / inactive on the Capabilities matrix.
- Head of Firm does NOT need this flag — appointing a Head unlocks Firm
  documents for that user on their firm immediately.
- Assign Head of Firm (`dashboard_assign_firm_head`) is NOT gated by this flag.
- Central control: toggling this flag on Central MUST sync to the content hub’s
  own database (remote DB wiring). The Head logs into the content hub site
  (Shared / White-label), not Central — that hub’s API must have the same
  Firm Documents / Head code deployed.

3.4.1 Who can appoint a Head of Firm
- Capability (Capabilities matrix): `dashboard_assign_firm_head`
  (“Assign Head of Firm”) — typically Power Admin / FinProms admin.
- Not part of the document rights model; only designates the head.
- ONE Head of Firm per firm; must already be a member of that firm.
- Head may be ANY role (manager, advisor, approver, client_admin, …).

3.4.2 Head of Firm rights (own firm only)
- Head of Firm can be ANY role (manager, advisor, approver, client_admin,
  admin-staff, user, …). Appointment is membership-based, not role-based.
- As soon as a user is appointed Head of Firm, they unlock “Firm documents”
  in the dashboard and have ALL document rights for THEIR firm: add, view,
  delete, archive, and granting those rights to firm members — no matrix tick
  and no Functionalities flag required.
- Documents are scoped to the firm.
- Frontend unlocks “Firm documents” via `firm_document_rights.is_firm_head` /
  merged `firm_documents_*` effective capabilities (any role).

3.4.3 Head grants rights to firm members (per document)
- Member rights are PER DOCUMENT (not firm-wide for view/delete/archive).
- The Head opens access rights from a key icon on each document row; popup
  grants / revokes any combination of add / view / delete / archive for that
  document to members of THEIR firm. Members only receive what the head grants.
- Granting `can_add` on a document also unlocks firm-level upload for that member.
- Cleared when a user leaves the firm or is discontinued.

3.4.3a Folders / subfolders
- Documents may sit in a folder tree (folders + nested subfolders) scoped to
  the firm. On upload, choose an existing folder or create a new folder /
  subfolder. Library UI is a nested expand/collapse table of folders with
  documents inside; unfiled documents are listed separately.
- Upload new document control sits directly above the library table.

3.4.3b Categories (taxonomy, like GC content types)
- Hub-scoped document categories (`firm_document_categories`) with name/slug.
- Capability `firm_documents_manage_categories` (“Manage firm document
  categories”) — blurred while Functionalities → Firm documents is off.
  Same admin CRUD pattern as General Compliance content types.
- Upload form category dropdown lists these options (optional).

3.4.4 Capabilities matrix — hub-wide (all firms)
- When Firm documents functionality is ON, these Capabilities are editable:
  - `firm_documents_view` — view documents for ANY firm on the hub
  - `firm_documents_add` — add documents for ANY firm on the hub
  - `firm_documents_delete` — delete documents for ANY firm on the hub
  - `firm_documents_archive` — archive documents for ANY firm on the hub
  - `firm_documents_manage_categories` — add/edit/delete category options
  - `firm_documents_manage_firm_access` — decide which firms may see
    Central / Network documents (allowlist). Those firms then appear in
    document access rights. Blurred while Firm documents functionality is off.
- These are hub-wide admin tools, distinct from Head / member per-document grants.

3.4.4a Central / Network documents — visible firms + access rights
- Two-step model for Central / Network (`firms.is_central`) documents:
  1) Visible firms allowlist — Head of Central / Network, OR any role with
     `firm_documents_manage_firm_access`, chooses which firms may see that
     firm’s documents (`GET/PUT /api/firm-documents/visible-firms`).
  2) Per-document access rights (key icon) — always lists OWN-firm users
     (same as 3.4.3) PLUS only the allowlisted firms (not every firm).
     Mode is `mixed`. Grant View / Add / Archive / Delete to members and/or
     firms. Firm grants apply to every current member of the grantee firm.
- Recipient firm members see shared Central docs in their own library under
  a “Shared from Central / Network” folder.
- Removing a firm from the allowlist also clears its per-document firm grants.
- Non-central firm documents keep per-member access only (3.4.3).

3.4.5 Activity logs (required for the whole flow)
- Every mutation in this flow is written to `activity_logs` (same hub audit
  trail as section 6A). Suggested action keys:
  - `firm.head.assign` — Head of Firm appointed
  - `firm.head.replace` — Head of Firm replaced
  - `firm.head.clear` — Head of Firm cleared
  - `firm.documents.member_rights.grant` — member document rights granted/updated
  - `firm.documents.member_rights.revoke` — member document rights revoked
  - `firm.documents.visible_firms.sync` — Central visible-firms allowlist updated
  - `firm.documents.firm_rights.grant` — firm-level Central doc access granted/updated
  - `firm.documents.firm_rights.revoke` — firm-level Central doc access revoked
  - `firm.documents.add` — document uploaded / created
  - `firm.documents.folder.create` — folder created
  - `firm.documents.view` — optional: record sensitive downloads if product
    requires audit of views (otherwise omit high-volume view noise)
  - `firm.documents.delete` — document permanently deleted
  - `firm.documents.archive` / `firm.documents.unarchive` — archive toggles
- Log payloads should identify firm id/name, actor, target user (for head /
  rights changes), grantee firm (for firm-level access), document id/name
  (for document actions), and granted rights flags — never store file binary
  contents; redact secrets.

4. WHITE-LABELLED HUBS (AND ADDITIONAL SHARED HUBS)

4.1 Multi-instance / Same Codebase + Separate Databases
- Central Hub Controller is the registry and remote-control source.
- New Shared hubs and White-labelled hubs are created by copying/reusing the
  SAME codebase onto another cPanel (or hosting) — the same operational model
  previously described for Shared → White-label, now owned by Central Hub.
- There will be MANY white-labelled hubs (and optionally more than one Shared).
- Code must remain the SAME for Central Hub, Shared hub(s), and all
  White-labelled hubs.
- Each hub instance (Central, each Shared, every White-label) has its OWN
  database — not a shared multi-tenant DB. Content, users, and settings for a
  content hub live in that hub's database only.
- Everything that differs per hub (especially branding) must be driven by DB:
  - Application name
  - Colour scheme (primary / secondary / accent)
  - Logo
  - Public page content (Home / Posts·Reels catalog / post detail copy)
  - Dashboard menu labels (sidebar separators + menu item names)
  - Other tenant-specific settings as needed
- Hub admins with `dashboard_manage_settings` can edit these branding fields
  (plus NEW banner days, page content, and dashboard menu labels) for the
  current hub via client-admin settings; they are returned on public GET /hub
  under branding / page_content / dashboard_nav and applied in the UI.
- Page content is stored on `hubs.page_content` (JSON). Defaults live in
  `App\Support\PageContentDefaults`. Posts and Reels share one catalog page
  (`/posts?type=post|reel`) so catalog copy is shared, with separate
  title/lead/search strings where the type differs. Placeholders such as
  `{credits}`, `{date}`, and `{count}` are substituted on the frontend.
- Dashboard menu labels are stored on `hubs.dashboard_nav` (JSON). Defaults live
  in `App\Support\DashboardNavDefaults`. Separators include context-specific
  Hub labels (Central / Shared / White-labelled). Menu items are keyed by path.
  Settings also control separator order (`section_order`), which separator each
  item sits under (`item_groups`), item order (`item_order`), and custom
  separators (`custom_*` keys in `sections` / `section_order`).
- Power Admin on CENTRAL HUB CONTROLLER is the control plane. The Central Hub
  DB stores a hub registry for every Shared and White-label hub, including
  deploy wiring so Central can reach that hub for management / content push:
  - hub_type — shared | white_label (and optionally central for the controller)
  - frontend_url — public site URL for that hub's deploy
  - api_url — optional backend API base URL
  - db_* — that hub's database connection (host, port, database, username,
    encrypted password, driver) so Central can push content / sync / act remotely
  - deploy_notes — free-text ops notes
  - Deploy contract: each content-hub deploy uses the SAME codebase with its OWN
    .env (its own DB_* + FRONTEND_URL / APP_URL). HUB_SLUG identifies the hub
    on that deploy. Central does NOT share the content hub's database.
  - When frontend_url is set, emails / Stripe return URLs prefer that hub URL
    over the global FRONTEND_URL env (on that hub's own deploy).
  - Power Admin hub detail shows a deploy checklist + copyable env snippet.
  - Hub detail is registry / deploy wiring only — Functionalities, Modules,
    Capabilities, and Subscriber credits are managed after selecting the hub
    in the Control hub switcher (not via boxes on hub detail).
  - When Central acts on a Shared/White-label hub, relative post/bundle media
    paths are resolved against that hub’s api_url / frontend_url media base
    (not Central’s APP_URL), so Shared catalog images load in the dashboard.
    Registry "ready" = active + frontend_url + remote DB credentials set.
  - Hub list badges: Wiring ready / Needs wiring.
- Content push / remote acting (Central → Shared or White-label): Power Admin
  (and other roles with capability, if enabled) select target hub(s); Central
  uses the stored remote DB connection (or API) to publish into / act on that
  hub's own database.

4.2 Private Access (White-labelled)
- White-labelled hubs are PRIVATE.
- Public users cannot subscribe.
- Client provides an Excel sheet of advisors.
- Advisors from that sheet are added into the application.
- Power Admin (on Central Hub) sets subscriber credits for the hub
  (dashboard + Capabilities):
  - Capability: `dashboard_manage_subscriber_credits` (private-hub dashboard tool)
  - Unlimited (default for white-label), OR
  - A fixed number of credits per subscriber per billing period.
- On Excel import, each new / reactivated advisor receives that allotment
  (unlimited flag, or balance set to the hub credit number).
- If Power Admin changes the credit number (or switches unlimited ↔ fixed)
  after advisors are already subscribed, existing balances are NOT changed
  mid-period; the new allotment is applied on the next monthly autorenew
  to all active advisors.
- Client admin (or Power Admin with import capability) can Discontinue an
  individual advisor: permanent end of access (WP FPSUB end equivalent).
  Discontinued advisors cannot log in, drop out of billing counts, and are
  not restored when the hub flips private again. Re-importing the same email
  restores them. Gated by Capabilities matrix key `advisor_discontinue`.
  Discontinue is shown on Hub → Users (`/my-dashboard/hub-users`), not on
  Import Users.
- Import Users page (`/my-dashboard/advisors`):
  - Users with `advisor_excel_template` (or Import / Submit) can download the blank
    Excel template, fill it offline.
  - Users with `advisor_excel_submit` upload the filled sheet; it is stored as
    Pending in import history with the user count, waiting for an importer.
  - Users with `advisor_excel_import` can import immediately or process a Pending
    submission from history.
  - History lists prior imports and pending submissions (who sent, when, file,
    user count / created / updated / skipped).
- When Power Admin switches a hub from private → public (Functionalities):
  - All Excel-imported advisors are SUSPENDED (not deleted): cannot log in,
    lose unlimited/subscription access, excluded from advisor billing counts.
  - Advisor Stripe auto-renew is canceled; pending advisor billings are canceled.
  - Private-related functionalities are turned off and public ones turned on
    (paid credits, one-off purchase, public subscribe; unlimited credits and
    advisor subscriber billing off).
- When the hub is switched back public → private:
  - Previously suspended imported advisors are REACTIVATED with the hub’s
    current subscriber-credit allotment and advisor_import subscriptions restored.
  - Auto-renew is NOT restarted automatically; client admin pays again after
    import / billing flow if needed.

4.3 Module recurring pricing for White-labelled (replaces advisor rate tiers)
- Advisor pricing tiers are RETIRED. Recurring charges use module catalogue +
  slot tables (editable under Modules → Module prices).
- Functionality: `charge_recurring_per_module` (default ON white-label / OFF shared).
- Slot tables (#1 SMTL, #2 SMC, #3 GC) by active user headcount bands
  (0–100 / 101–250 / 251–500 / 501+). Rate + network margin per band.
- Import Option B: rate from TOTAL active users with that module (not suspended,
  not discontinued); invoice charges RATE × THIS IMPORT BATCH only; due today.
- Same batch renews monthly on the import anniversary day (active users only).
- Renew day (`/my-dashboard/advisor-renewal`): charge hub payment card for ALL
  due unpaid invoices (one-time + recurring). Grace day (≥ renew day): after
  grace, unpaid recurring seat invoices suspend those users; unpaid one-time
  module invoices disable those modules.
- Discontinue (`advisor_discontinue`) applies to ANY hub user (not only advisors);
  discontinued users are excluded from future recurring seat counts.

4.4 Remote control of content hubs (from Central Hub Controller)
- Capability: `dashboard_control_white_label_hubs` — “Control hubs remotely”
  (name may be generalized to cover Shared + White-label; replaces the old
  per-form Hub dropdown / `dashboard_push_content`).
- Users with this capability on CENTRAL HUB (typically Power Admin) get a hub
  switcher at the top of the Central Hub dashboard.
- Selecting Central Hub context → platform tools only (registry, checklists, etc.).
- Selecting a Shared or White-label hub → dashboard menus/tools follow THAT
  hub’s Capabilities matrix for the user’s role (e.g. View posts). Creating
  posts / types / categories / tags is Central-only (Central content library);
  while a content hub is selected those pages are list-only. Bundles and other
  hub tools still write to THAT hub’s own database when enabled.
- Dashboard “Website” / “Back to website” always opens THIS deploy’s public
  site (`/`), gated by `member_view_site_pages` on the control-plane (Central)
  matrix for that user. It must NOT open the selected Shared / White-label
  `frontend_url` (cross-origin login caused flicker → blank screen).
  Power Admin / FinProms Admin cells for `member_view_site_pages` always
  read/save on Central (even while the hub switcher is on a content hub), so
  enabling the capability turns on the Central Website button.
- APIs: `GET/PUT /client-admin/acting-hub` (and power-admin / admin aliases).
  Authenticated `GET /hub` includes `hub_switcher` + acting effective caps when
  on Central Hub with remote-control capability.
- Target hub for the switcher must be active with remote DB credentials
  configured on the Central Hub registry (deploy wiring). Selecting a hub for
  remote control does NOT require “Receive content from Central Hub”.
- “Receive content from Central Hub” (`receive_content_from_shared`) only gates
  Central content library distribute / content push — not the hub switcher.
- Central content library (capability `dashboard_central_content_library`,
  Central Hub only):
  - Create manual posts one-by-one or bulk Excel (template download like
    advisor import). Posts remain in the Central DB.
  - AI posts tab is under development (empty stub).
  - Distribute non-archived (ready) library posts to Shared / White-labelled
    hubs. Copies are inserted into the target hub DB. Re-distributing a post
    to a hub that already has it (tracked via content_pushes + remote row)
    skips the insert — no duplicate. Archive is optional:
    it retires a post from the distribute pool with required remarks but does
    not delete or hide it from the Central library list. Unarchive clears
    remarks and restores the post to the distribute pool.
  - Central posts list lives on `/my-dashboard/posts` (ready + archived, with
    search/filters and “published on” hubs). Editing a Central post also
    updates the copies on hubs it was successfully distributed to.
  - Central library page tabs: Create / AI posts / Distribute / Archive
    (archive / unarchive is its own tab, not nested under Distribute).
  - Distribution checks: non-archived posts only; AI posts only to hubs with
    `ai_posts`; manual posts only to hubs with `manual_posts`.
  - Target hubs list includes every active Shared and White-labelled registry
    hub. Selectable (eligible) hubs need Receive content from Central, remote
    DB wiring, Social Media Template Library, and Manual or AI posts. Ineligible
    hubs stay visible but disabled with a reason. White-label hubs default to
    receive + manual posts (same as Shared).
  - Types / categories / tags with Central library:
    - Central keeps its own taxonomy tables (`content_types`, `categories`,
      `tags`) plus type/categories/tags names stored on each Central post.
    - On create (one-by-one or Excel), Central upserts any new type /
      category / tag names into Central’s own taxonomy tables so the library
      form and Manage types/categories/tags stay in sync.
    - The Central library create form accepts existing names or new free-text
      names; Manage types / categories / tags pages on Central remain the
      full CRUD admin for Central taxonomy.
    - On distribute, the push upserts by **name** into the target hub’s own
      DB: any type, category, and tag used on the Central post is created on
      the target if missing (or refreshed if a matching name already exists),
      then the post copy is inserted with the same type/categories/tags values.
    - This is a copy/upsert, not a live link back to Central. Each Shared /
      White-label hub keeps its own taxonomy tables; local-only types/
      categories/tags on a hub are left alone unless a distributed post
      carries that name.
    - While the hub switcher is on a Shared / White-label hub, Manage types /
      categories / tags writes only to THAT hub’s DB (for local catalog work),
      not Central’s.
    - Public member catalog taxonomy GETs (`/types`, `/categories`, `/tags`)
      require `member_browse_catalog` OR (when authenticated) Central library /
      manage-types/categories/tags capabilities — Central keeps member catalog
      off, so Power Admin still loads taxonomy for the Central library form
      via the dashboard capability OR.
- Media for remote posts is stored as a public URL reachable from Central /
  source storage (file uploaded via controlling instance, path saved on the
  target hub DB).
- While a target hub is selected, list/create/update/delete that hub’s content
  via the normal dashboard endpoints (`/posts`, `/types`, `/categories`, `/tags`,
  `/bundles`) or `/hub-content/...` — both use the acting hub (no `hub_id`).
  IDs in those requests are remote hub database IDs.
- Shared Hub no longer hosts this cross-hub control plane for itself + others;
  that responsibility moves to Central Hub Controller.

6B. HUB BACKUP & RESTORE
--------------------------------------------------------------------------------
- Dual storage: each scheduled/manual backup is saved on the hub's own server
  (storage/app/backups/{slug}/) AND a copy is stored on Central
  (storage/app/backups/central/{slug}/).
- Central Hub also backs itself up (local + Central store on the same server);
  Power Admin can download Central archives. Prefer off-server copies for DR.
- Schedule is per hub, set from Central (Power Admin + pa_manage_hub_backups):
  enabled, time (HH:MM), timezone, daily|weekly (+ weekday), retention local /
  Central. Settings sync to content hubs via remote DB push when wired.
- Scheduler: `hubs:run-due-backups` every minute (requires schedule:run cron on
  each deploy). Central also triggers due remotes via hub api_url when set.
- Restore from Central uses the Central-stored zip; content hubs receive the
  archive on POST /api/internal/hub-backups/restore (X-Hub-Backup-Key).
- Env (optional): CENTRAL_API_URL on content hubs for independent upload;
  HUB_BACKUP_SECRET shared fallback; per-hub backup_token auto-generated.
- Capability: pa_manage_hub_backups (Power Admin platform checklist).

6A. ACTIVITY LOGS & ACTIVITY REPORT
--------------------------------------------------------------------------------
- Every meaningful user activity is recorded in an activity_logs audit trail
  (per hub), including:
  - Auth: register, email verified, login OTP sent/verified, terms accepted,
    login, logout, failed login, blocked login (suspended / discontinued /
    invite-only / email unverified)
  - Successful mutating API actions (POST / PUT / PATCH / DELETE): content,
    plans, settings, advisor import/discontinue, billing, capabilities, hubs,
    purchases, subscriptions, etc.
  - Firm Head & Firm Documents (section 3.4): appoint/replace/clear head,
    grant/revoke member document rights, and document add / delete / archive
    (and view/download if audited) — action keys `firm.head.*` and
    `firm.documents.*`
- Sensitive fields (passwords, secrets, card data) are NEVER stored; payloads
  are redacted / truncated.
- Activity report (aggregates): totals, unique users/actions, counts by action,
  by user, and by day — filterable by user, action, date range, and text search.
- WHO CAN SEE the logs and report is gated by Capabilities matrix key
  `dashboard_view_activity_logs` (hub-admin dashboard group). Applicable roles:
  finproms_admin, client_admin, manager, and power_admin (when enabled for that
  hub / when acting remotely). Power Admin toggles this per hub / role on the
  Capabilities screen (Central Hub).
- APIs (hub_can:dashboard_view_activity_logs):
  - GET /api/client-admin/activity-logs (+ /power-admin/…) — paginated feed
  - GET /api/client-admin/activity-logs/report (+ /power-admin/…) — aggregates
- Frontend: Activity logs page under hub-admin and Power Admin shells, shown
  only when the viewer’s role has the capability.

6B. ACTIVE SESSIONS / FORCE LOGOUT
--------------------------------------------------------------------------------
- Capability: `dashboard_manage_active_sessions` (Hub operations group on the
  Capabilities matrix). Applicable roles: all matrix roles; defaults ON for
  hub-admin style roles, OFF for approver / advisor / admin-staff / user until
  Power Admin enables them.
- Users with this capability can:
  - See which users currently have active login sessions (Sanctum tokens) on
    the current hub (or acting remote hub’s own database).
  - Force-logout any listed user, which deletes all of that user’s tokens so
    they must sign in again.
- Force-logout of the viewer’s own account ends their session immediately.
- Mutations are written to activity_logs (`auth.force_logout`).
- APIs (hub_can:dashboard_manage_active_sessions):
  - GET /api/client-admin/active-sessions (+ /power-admin/…) — logged-in users
  - POST /api/client-admin/active-sessions/{userId}/force-logout (+ /power-admin/…)
- Frontend: Active sessions page under /my-dashboard (nav + Capabilities gate).

7. ARCHITECTURE PRINCIPLES (DERIVED FROM REQUIREMENTS)
--------------------------------------------------------------------------------
- Single codebase for Central Hub Controller + Shared hub(s) + all White-labels.
- Three instance roles: central (control plane), shared (public/content hub),
  white_label (private client hub).
- Roles: power_admin, finproms_admin, client_admin, manager, approver, advisor, user.
- Separate frontend shells: member catalog app (on Shared / White-label), and
  one universal Dashboard shell at /my-dashboard (tools from Capabilities +
  Power Admin pa_* checklist on Central Hub).
  Legacy /client-admin and /power-admin routes redirect to /my-dashboard.
- Tenant/hub configuration stored in database (branding, flags, rights).
- Feature flags / rights checklists must drive behaviour AND dashboard menus,
  not hard-coded forks. Power Admin has its own platform capability checklist
  (separate from per-hub checklists), stored/managed on Central Hub.
- Central Hub Controller is the configuration + remote-control source of truth
  (registry + remote DB credentials on Central; each content hub has its own DB).
- Shared Hub is a content hub only — not the control plane.
- New Shared and White-label instances are spawned by copying code to another
  cPanel and registering them on Central Hub.
- Design for future: AI generation (FinProms admin), in-app edit, compliance,
  firm head + firm documents, more features.
- Settings that vary (e.g. NEW-banner duration) come from the database.
