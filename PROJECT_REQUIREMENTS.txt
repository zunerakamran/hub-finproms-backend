--------------------------------------------------------------------------------
1. PRODUCT OVERVIEW
--------------------------------------------------------------------------------
- FinProms content platform: social media posts, reels, etc.
- Users subscribe, receive credits, spend credits on posts/reels, then download.
- Branding (colours, logo, etc.) must come from the database so each hub
  can look different without code changes.

THREE HUB TYPES (same codebase, separate deploys / databases):

  A) CENTRAL HUB CONTROLLER ("Central Hub")
     - Platform control plane ONLY — not a member content catalog for end users.
     - Where Power Admin remotely controls ALL hubs (Shared + White-labelled).
     - Where new Shared hubs and White-labelled hubs are registered, wired, and
       spawned (copy same codebase onto another cPanel / hosting instance).
     - Owns the hub registry, remote DB credentials, Functionalities / Modules /
       Capabilities for every hub, platform payment methods, and Power Admin tools.
     - Does NOT replace day-to-day content work on Shared or White-label hubs.

  B) SHARED HUB
     - A normal content hub for FinProms public/shared catalog (posts, reels,
       plans, subscriptions, purchases).
     - Operated day-to-day by FinProms admin (and staff roles as enabled).
     - Is NOT the control plane. It is controlled remotely by Central Hub
       (same remote-control pattern as white-labelled hubs).
     - May still receive content / configuration push FROM Central Hub when
       those features are enabled.
     - Additional Shared hubs can be created the same way as white-labels:
       copy codebase to another cPanel, own DB + .env, register on Central Hub.

  C) WHITE-LABELLED HUB
     - Private client hub (advisor Excel import, restricted options).
     - Same codebase; own database; branding from DB.
     - Controlled remotely by Central Hub (hub switcher / acting hub / remote DB).

Deploy rule:
- ONE codebase for Central Hub Controller + Shared Hub(s) + all White-labelled hubs.
- Each instance has its OWN database and .env (HUB_SLUG, DB_*, FRONTEND_URL / APP_URL).
- Central Hub is the master registry and remote-control source — not Shared Hub.


--------------------------------------------------------------------------------
1A. CENTRAL HUB CONTROLLER (CONTROL PLANE)
--------------------------------------------------------------------------------
- Purpose: separate remote control from content hubs so Shared Hub no longer
  controls itself and other hubs from the same place.
- Power Admin logs into Central Hub and from there:
  1) Hub registry — create / list / edit Shared hubs AND White-labelled hubs
  2) Deploy wiring per hub — frontend_url, api_url, db_* (encrypted password),
     deploy_notes, copyable env snippet / checklist
  3) Hub Functionalities + Modules checklists per hub (section 5.1 / 5.1A)
  4) User capabilities matrix per hub (section 5.2)
  5) Power Admin's OWN capabilities checklist (section 5.3)
  6) Platform payment methods and other platform settings
  7) Remote control / hub switcher — act on a Shared or White-label hub's own
     database (content, types, categories, tags, bundles, settings, etc.) when
     wiring + receive_content / remote-control flags allow
  8) Code updates — publish release (+ optional zips), refresh versions, select
     hubs and apply packages (Phase 1 tracking + Phase 2 apply)
- Spawning a new hub (Shared or White-label):
  - Ops copies the SAME codebase to another cPanel (or hosting).
  - New instance gets its OWN DB + .env (HUB_SLUG, DB_*, URLs).
  - Power Admin registers that hub on Central Hub and stores deploy wiring /
    remote DB credentials so Central can reach it.
  - Hub type is set in registry (shared | white_label); packaging modules and
    default Functionalities follow that type.
- Central Hub DB stores the hub registry for EVERY Shared and White-label hub.
  Content catalogs for those hubs live in EACH hub's own database — Central
  does NOT share those databases.
- Registry "ready" = active + frontend_url + remote DB credentials set.
  Hub list badges: Wiring ready / Needs wiring; also code version badges
  (Up to date / Behind latest / Unknown / Check failed).
- Central Hub itself is NOT a substitute Shared catalog; member browse/buy
  flows belong on Shared / White-label instances.


--------------------------------------------------------------------------------
1B. CODE UPDATES ACROSS HUBS (PHASE 1 — TRACKING)
--------------------------------------------------------------------------------
Purpose: update the product once, then from Central see which existing Shared /
White-label hubs are on that release. This is NOT new-hub spawn (copy code to a
new cPanel). Spawn stays manual; Phase 1 only tracks versions after you deploy
via Git (backend) and Git/FTP build (frontend).

Version identity (every deploy — Central, Shared, WL):
- Root file VERSION (default) and/or .env APP_VERSION / FRONTEND_VERSION.
- Public GET /api/version → { version, backend_version, frontend_version, slug,
  type, is_control_plane }. Also exposed on GET /api/hub as hub.code.
- After each ship: bump VERSION (or set APP_VERSION on that hub's .env) and set
  FRONTEND_VERSION to match the frontend build you FTPed.

Central registry:
- hub_releases table: publish version + optional backend/frontend versions + notes;
  one row marked is_latest.
- Per hub row: code_version*, code_version_status (up_to_date|behind|ahead|
  unknown|error), source (local|remote_api|manual), checked_at, error.
- Power Admin (pa_manage_hubs):
  - GET/POST /api/power-admin/releases — list / publish latest
  - POST /api/power-admin/hubs/refresh-versions — poll all hubs
  - POST /api/power-admin/hubs/{hub}/refresh-version — poll one
    (Central = local config; content hub = GET {api_url}/version)
  - POST /api/power-admin/hubs/{hub}/mark-version — manual record when API
    unreachable
- Hub admin payloads include code_update { reported_version, status,
  status_label, latest_version, … }.

Ops workflow (Phase 1 — track only):
  1) Ship code (git pull backend; build + FTP frontend) on chosen hubs.
  2) Ensure APP_VERSION / FRONTEND_VERSION (or VERSION file) matches the release.
  3) On Central: Publish release (e.g. 1.2.0) → Refresh versions → see badges.

--------------------------------------------------------------------------------
1C. CODE UPDATES ACROSS HUBS (PHASE 2 — APPLY TO SELECTED HUBS)
--------------------------------------------------------------------------------
Purpose: from Central, choose which existing hubs receive a release package
(backend zip and/or frontend dist zip). Still not new-hub spawn.

Release artifacts (stored on Central disk: storage/app/private/releases/{ver}/):
- On publish (multipart) or POST /api/power-admin/releases/{id}/artifacts:
  backend_zip, frontend_zip (optional each; at least one required to apply).
- backend zip = Laravel app tree (prefer include vendor/). Never overwrites
  .env, storage/app|framework|logs, bootstrap/cache, .git.
- frontend zip = Vite dist (dist / dist-shared / … root stripped). Extracted to
  hub.code_frontend_path (Central registry) or CODE_UPDATE_FRONTEND_PATH on that
  server.

Apply:
- POST /api/power-admin/releases/apply { release_id?, hub_ids: [] }
- Central marks hub code_apply_status=updating, ensures code_update_token
  (never reuses backup/restore/GC/deploy tokens), pushes token +
  code_frontend_path via white-label DB sync when remote DB wired.
- Content hub: POST {api_url}/internal/code-updates/apply with
  X-Hub-Code-Update-Key; hub downloads artifacts from Central
  GET /api/internal/code-updates/artifacts/{release}/{backend|frontend},
  extracts, writes VERSION + storage marker, runs migrate --force, clears caches.
- Central self-apply uses local artifact files (no HTTP loopback).
- Auth: code_update_token OR HUB_CODE_UPDATE_SECRET only (not backup keys).
- Per hub: apply_status (idle|updating|applied|failed), target_version,
  applied_at, apply_error; then refresh reported version.

UI (Central Hubs page): upload zips with publish, multi-select hubs, Apply to
selected (choose latest or a prior ready_to_apply release for deploy package
rollback — distinct from module disaster recovery §6B.1); Update history
table (filter by hub). Hub detail: code_frontend_path.

Update history (append-only on Central):
- Table hub_code_update_events: hub, release, version, action (apply|
  mark_manual), status (success|failed), message, backend/frontend/migrated
  flags, triggered_by, finished_at.
- Written on every Apply and manual “mark version”.
- GET /api/power-admin/releases/history?hub_id=&limit=
- Also included as overview.history on GET /api/power-admin/releases.

Packaging tips:
- Backend: zip the backend repo (exclude .env / storage contents); include vendor
  if target cPanel has no composer.
- Frontend: zip the contents of dist-* after npm run build:shared / build:myhub.

2. SHARED HUB — STEP 1 CORE FEATURES
--------------------------------------------------------------------------------
(Shared Hub = content hub. Platform control lives on Central Hub Controller.)

2.1 Content classification (THREE separate fields)
- TYPE — what the item is: post, reel, etc. (managed list; drives reel play button).
- CATEGORY — topical/grouping category (separate from type; e.g. product themes).
  Categories support an optional icon: curated Font Awesome key (`icon`) and/or
  uploaded image (`icon_path` → public `icon_url` via /api/media). Upload wins
  over font icon when both would apply. Central Categories admin lists icons to
  pick from and accepts an image upload; home “Browse by Categories” renders
  upload → font icon → name initial. Icons sync to content hubs on distribute.
- TAGS — free labels for filtering (separate from type and category).
- Every content item has type + category + tags. Do NOT treat category as type.

2.2 Content browsing & listing UX
- Hub catalog / main member pages require login. Unauthenticated visitors are
  sent to the login screen and must not see the hub main/catalog UI.
- Users browse posts, reels, and other types.
- Listing page uses a 3-column grid (2 columns on tablet, 1 on mobile).
- For REELS: admin can upload a video when type is Reel.
- Reel video autoplays (muted, looping) on listing and detail pages.
- A play/pause “Reel” control sits at the top of the video to mark it as a reel
  and let the viewer pause/resume.
- Reels without a video still show the legacy centered play indicator on listing.
- "NEW" banner on new posts/reels:
  - Shown when the item is still within the "new" window.
  - Duration (e.g. number of days) is taken from the DATABASE (configurable
    setting), not hard-coded.

2.2a Shared Hub self-registration email verification
- When public self-registration is enabled (`public_subscribe` / not invite-only),
  new members must verify their email before they can sign in.
- Register creates the account with `email_verified_at` null, does NOT issue a
  Sanctum token, and sends a hub-branded verification link
  (`{frontend}/verify-email?token=…&email=…`). Link expires in 60 minutes.
- Verify endpoint marks the email verified, sends the welcome email, and returns
  an auth token so the member is signed in.
- Unverified members are blocked at login with `email_verification_required` and
  may request a resend (throttled).
- Admin-created and Excel-imported users are marked verified immediately.
- Existing accounts are backfilled as verified by migration so they are not locked out.
- Email template catalog event: `email_verification` (editable like other templates).
- APIs: POST /api/auth/verify-email, POST /api/auth/resend-verification.
- Frontend: Register shows “check your email”; VerifyEmail page; Login offers resend.

2.2b Two-factor authentication (login OTP) — per user (all hub types)
- NOT a hub Functionalities checkbox. Each user opts in from Update profile
  (`users.two_factor_enabled`, default OFF). Only that user gets email OTP
  after a successful password check on every sign-in.
- Enabling / disabling 2FA (and changing email) requires `current_password`.
- Login returns `otp_required` + `otp_challenge` (no Sanctum token yet)
  only when that user has 2FA enabled (and MFA is not enabled).
  A 6-digit code is emailed (hub From address / MAIL_FROM fallback).
  Code expires in 10 minutes; max 5 failed attempts; resend throttled 60s.
- APIs: POST /api/auth/verify-login-otp, POST /api/auth/resend-login-otp.
- Public GET /hub exposes `auth.login_otp_per_user` (true) and
  `auth.login_otp_required` (always false; legacy clients).
- Email template catalog event: `login_otp` (always available to edit).
- Frontend Login shows a second step when the login response has otp_required.
- Activity logs: `auth.two_factor_otp_chosen` / `auth.two_factor_otp_disabled`
  when the user toggles email OTP on Update profile (`properties.method` = otp).
- Profile page (all authenticated users): Update profile — name, email,
  avatar (profile picture), email OTP toggle, and MFA toggle (see 2.2b2).
  API: PUT/PATCH/POST /api/auth/profile (POST for multipart avatar).
  Changing email clears verification and sends a new verification link.
  Avatar stored on public disk (`avatars/{user_id}/…`); URL via /api/media/.

2.2b2 Authenticator MFA (Microsoft Authenticator / TOTP) — per user
- Second checkbox on Update profile (`users.mfa_enabled`, default OFF).
  Compatible with Microsoft Authenticator and any RFC 6238 TOTP app.
- Mutually exclusive with email OTP: enabling one clears the other.
- Enabling MFA is two-step: (1) profile `mfa_enabled=true` + `current_password`
  stores an encrypted secret and returns `mfa_setup` { secret, otpauth_uri,
  issuer, account } with `mfa_confirmation_required`; user is `mfa_pending`
  until confirmed. (2) POST /api/auth/mfa/confirm with app code + password
  sets `mfa_enabled` + `mfa_confirmed_at`.
- Optional: POST /api/auth/mfa/setup to resume/regenerate pending setup.
- Disabling MFA (profile `mfa_enabled=false` + password) clears secret.
- Login: when MFA is enrolled, returns `mfa_required` + `mfa_challenge`
  (no token yet). POST /api/auth/verify-login-mfa with email, challenge, code.
  MFA takes precedence over email OTP if both were somehow set.
- Public GET /hub: `auth.login_mfa_per_user` = true.
- Activity logs (choice tracking):
  `auth.mfa_setup_started`, `auth.mfa_chosen`, `auth.mfa_disabled`,
  plus login `auth.login_mfa_required` / `auth.login_mfa_verified`
  (`properties.method` = mfa).

2.2c Terms & Conditions (all hub types)
- Capability matrix key: `dashboard_manage_terms` (“Manage terms & conditions”)
  in Hub operations. Defaults ON for hub-admin style roles on Shared and
  White-label (and available on Central). Who may edit content is controlled
  per role on the Capabilities matrix.
- Hub stores rich HTML Terms & Conditions (`hubs.terms_and_conditions` JSON:
  content, version, updated_at). Each hub type seeds relevant default copy
  (Shared catalogue / White-label private firm / Central control plane) which
  capable users can edit via a rich-text editor.
- On first login (and when the version changes after an edit), authenticated
  users must view and accept the current terms before using the app.
  Acceptance is stored on the user: `terms_accepted_at`, `terms_accepted_version`.
- APIs: GET/PUT /api/client-admin/terms, POST /api/client-admin/terms/reset
  (hub_can:dashboard_manage_terms); POST /api/auth/accept-terms (auth).
- Public GET /hub includes `auth.terms` { required, version, content }.
- Frontend: /my-dashboard/terms admin page; TermsGate modal after login.

2.2d Privacy Policy (all hub types) — UK GDPR Phase 1
- Separate from Terms & Conditions (section 2.2c). Terms remain contractual;
  Privacy Policy is the transparency notice under UK GDPR + DPA 2018.
- Capability matrix key: `dashboard_manage_privacy` (“Manage privacy policy”)
  in Hub operations. Defaults ON for hub-admin style roles (same pattern as
  `dashboard_manage_terms`); Power Admin toggles per hub / role on Central.
- Hub stores rich HTML Privacy Policy (`hubs.privacy_policy` JSON: content,
  version, updated_at). Seed sensible default copy per hub type (Shared /
  White-label / Central) covering: who the controller is, what personal data
  is processed, purposes, lawful bases, retention summary, recipients /
  processors (e.g. Stripe, email, hosting), international transfers if any,
  individual rights, and how to contact the hub / raise a complaint with the
  ICO. Capable users can edit via rich-text editor.
- On first login (and when the version changes after an edit), authenticated
  users must view and acknowledge the current privacy policy before using the
  app (same gate pattern as Terms). Acceptance stored on the user:
  `privacy_accepted_at`, `privacy_accepted_version`.
- Public GET /hub includes `auth.privacy` { required, version, content }.
- APIs: GET/PUT /api/client-admin/privacy, POST /api/client-admin/privacy/reset
  (hub_can:dashboard_manage_privacy); POST /api/auth/accept-privacy (auth).
- Frontend: /my-dashboard/privacy admin page; PrivacyGate (or combined
  legal-gate after Terms) after login.
- Remove or shorten the generic “Privacy” subsection inside default Terms so
  it points to the Privacy Policy instead of duplicating it.
- See section 6E for the full UK GDPR roadmap (DSAR, erasure, retention, etc.).

2.2e Cookie Notice (all hub types) — UK GDPR / PECR Phase 5
- Separate from Terms and Privacy. Banner informs visitors about essential
  cookies (session + CSRF); not a full consent preference centre while no
  non-essential cookies exist.
- Capability matrix key: `dashboard_manage_cookies` (“Manage cookie notice”)
  in Hub operations. Same default pattern as Terms / Privacy.
- Hub stores rich HTML Cookie Notice (`hubs.cookie_notice` JSON: content,
  version, updated_at). Defaults per hub type (Shared / White-label / Central).
  Capable users edit via rich-text editor; Save/Reset bumps version.
- Public GET /hub includes `auth.cookies`
  { essential_only, required, version, content, updated_at }.
- APIs: GET/PUT /api/client-admin/cookies, POST /api/client-admin/cookies/reset
  (hub_can:dashboard_manage_cookies).
- Frontend: /my-dashboard/cookies admin page; CookieBanner shows when
  localStorage version ≠ current hub version (OK dismisses until next bump).
- No authenticated accept-gate (unlike Terms/Privacy) — PECR transparency
  banner is sufficient for essential-only cookies.

2.3 Content metrics
- Each post/reel tracks:
  - reach — unique impression when a user scrolls the listing and the post
    enters their viewport (POST /api/posts/reach with post_ids)
  - views — when a user opens the post detail page (GET /api/posts/{id})
  - buy count — when a user purchases the post
- Metrics are stored and shown on listing/detail for members according to their
  active subscription plan’s visibility flags (Power Admin / hub-admin can
  configure these on each plan):
  - Basic (default): reach only
  - Standard (default): reach + views
  - Premium (default): reach + views + buys
- Hub admins, Power Admin (when acting on that hub), and unlimited-credit
  advisors see all three metrics.
- Non-subscribers do not see metric counts.
- Plan fields: show_reach, show_views, show_buys (editable via subscription plan
  CRUD under Power Admin and hub-admin when dashboard_manage_plans is enabled).
- API responses include visible_metrics so the frontend knows what to render.

2.4 Subscriptions & Credits
- Users subscribe and receive credits.
- Credits are spent when buying posts/reels or post bundles.
- After purchase, users can preview the content in-app (no file download).

2.4a Post bundles
- Capability-gated (Capabilities matrix: dashboard_manage_bundles) — roles that
  Power Admin enables can create/edit bundles in the hub-admin dashboard.
- Website visibility is gated separately by `member_browse_bundles` (Member
  catalog group on the Capabilities matrix). When off for a role, Bundles nav
  and /bundles pages are hidden for that role; turn off for every role to hide
  bundles for the whole hub. Defaults ON for Shared / White-label, OFF on Central.
- A bundle has a title, description, and total credits_cost (bundle price).
- Creators can include existing posts/reels and/or create new posts/reels and
  attach them in the same flow.
- Members browse bundles when `member_browse_bundles` is on; purchasing a
  bundle spends the bundle’s total credits and unlocks every post in the bundle.
- Invoices are generated for bundle purchases (type bundle_purchase).

2.5 One-off / Non-subscriber Purchases
- Users who are NOT subscribed can still buy individual posts/reels.
- Pricing rule: content is priced in credits (no pound display in catalog copy).

2.6 Invoices
- Invoices are generated for:
  a) Subscriptions
  b) Individual post/reel purchases

2.7 Roles & separate dashboards
There is ONE universal dashboard shell at /my-dashboard for every role.
What each user sees (sidebar + home cards) is driven by the Capabilities
matrix (and Power Admin’s own pa_* checklist for platform tools on Central Hub).

The member catalog (posts / bundles / plans) stays on the main website of
Shared / White-label hubs by default. Central may optionally expose a public
site shell when Power Admin enables member_* caps on Central’s own matrix.
Staff and members open Dashboard from the main site nav; login lands on
/my-dashboard. Legacy /client-admin and /power-admin URLs redirect into
/my-dashboard. Members never see tools that are not enabled for ANY of their
roles (see §2.7.1 multi-role rule).

MULTI-ROLE MODEL (REQUIRED — target behaviour):
- PREVIOUSLY: each user had exactly ONE role (`users.role`).
- NOW: each user MAY hold ONE OR MORE roles at the same time on that hub’s
  user store (e.g. manager + approver, client_admin + approver,
  advisor + firm_admin).
- A user MUST always have at least one role.
- Capability evaluation uses the UNION of all assigned roles (§2.7.1).
- Canonical role keys stay stable; display names remain overridable. New
  system roles `network_admin` and `firm_admin` are added to the catalog and
  matrix (§2.7 / §3.4 / §5.2). Multi-role itself only changes user↔role
  cardinality from 1:1 to many:many.
- Full rules, equal multi-role model, migration, and affected areas:
  see §2.7.1.

ROLES (canonical list — role keys are stable; display names are overridable
via hub `role_display_names` / Manage roles — including Network Admin and
Firm Admin):

  1) POWER ADMIN (power_admin) — platform developers / us
     - Logs into CENTRAL HUB CONTROLLER (control plane).
     - Manages hubs (Shared + White-label), hub Functionalities + Modules
       checklist (section 5.1 / 5.1A), user capabilities matrix (section 5.2),
       payment methods, and Power Admin's OWN capability checklist (section 5.3).
     - Remotely controls Shared and White-labelled hubs (hub switcher / acting
       hub) when those capabilities and wiring allow.
     - What a power_admin can do on that control plane is gated by the separate
       Power Admin capabilities checklist (not the per-hub member/dashboard lists).

  2) FINPROMS ADMIN (finproms_admin) — Shared hub admin
     - Day-to-day operator of a SHARED hub (content hub).
     - Manages that Shared hub’s content, types, categories, tags, plans,
       settings, etc.
     - Can generate AI posts (when built) and may control white-labelled hubs
       via Central Hub remote tools ONLY if Power Admin enables that capability
       for their role — Preferred path is Power Admin on Central Hub for
       cross-hub control; FinProms admin focus is Shared hub day-to-day ops.
     - Uses the hub-admin shell; capabilities come from THAT Shared hub's
       dashboard checklist (section 5.2), managed on Central Hub.

  3) CLIENT ADMIN (client_admin) — white-labelled hub admin
     - Operator of ONE white-labelled hub.
     - Restricted vs FinProms admin; only tools Power Admin enables for that hub.
     - Uses the same hub-admin shell; capabilities from THAT hub's dashboard checklist.

  4) NETWORK ADMIN (network_admin) — head of the Central / Network firm
     - NEW system role (multi-role compatible). Default display name
       “Network Admin” (renameable per hub).
     - Means: this user is a Head of the hub’s single Central / Network firm
       (`firms.is_central = true`, default name “Central / Network”).
     - User MUST be a member of that Central / Network firm (`users.firm_id`
       points at the central firm). Assigning `network_admin` to a user of a
       non-central firm is rejected.
     - MULTIPLE Network Admins allowed per hub (any number of central-firm
       members may hold `network_admin`). Assigning another does NOT revoke
       existing Network Admins. `firms.head_user_id` is an optional primary
       contact only (not exclusive headship).
     - Unlocks Document Repository (Firm Documents) full rights for the
       Central / Network firm only — see §3.4.
     - Other screens still follow the §5.2 matrix UNION for this role column
       (hub-wide firm_documents_* caps remain separate from own-firm head rights).
     - May be combined with other non–control-plane roles (e.g. manager,
       approver, user).
     - Website Template Library: with `wc_request_deployments` +
       `wc_assign_website_templates` + `wc_request_go_live` (default ON),
       Network Admin requests a site for the network, assigns Website Admins,
       and can request go-live for sites they requested (§3.3d).

  5) FIRM ADMIN (firm_admin) — head of a member firm
     - NEW system role (multi-role compatible). Default display name
       “Firm Admin” (renameable per hub).
     - Means: this user is a Head of THEIR firm — the firm on
       `users.firm_id`. Example: user belongs to Firm1 and is assigned
       `firm_admin` → they are Head of Firm1.
     - User MUST belong to a non-central firm. Do NOT assign `firm_admin` to
       Central / Network firm members — use `network_admin` instead.
     - MULTIPLE Firm Admins allowed per member firm. Assigning `firm_admin`
       to another member does NOT revoke existing Firm Admins for that firm.
     - Unlocks Document Repository (Firm Documents) full rights for THEIR
       firm only — see §3.4.
     - Other screens follow the §5.2 matrix column for `firm_admin`.
     - May be combined with other roles (e.g. advisor + firm_admin,
       manager + firm_admin).
     - Website Template Library: with `wc_request_deployments` +
       `wc_assign_website_templates` + `wc_request_go_live` (default ON),
       Firm Admin requests a site for THEIR firm, assigns Website Admins, and
       can request go-live for sites they requested (§3.3d).

  6) WEBSITE ADMIN (website_admin) — firm/network website editor
     - NEW system role (multi-role compatible). Default display name
       “Website Admin” (renameable per hub).
     - Firm- or network-scoped editor for Website Template Library
       deployments / Website Content Pre Approval editing.
     - MULTIPLE Website Admins allowed per firm or network. A user must
       belong to a firm (`users.firm_id`); the role may be held alongside
       other non–control-plane roles (e.g. advisor + website_admin).
     - Default matrix ON: `wc_edit_sections`, `wc_submit_change_requests`.
     - Assigned to website deployments by Network Admin / Firm Admin (or
       other roles with `wc_assign_website_templates`) via multi-select.
       One website may have MANY Website Admins (`wc_template_request_website_admins`
       pivot). `assigned_advisor_id` remains the primary content/cPanel owner
       (first selected Website Admin) for section scoping.
     - Picker eligibility uses Delegated compliance access (§2.7.0a) — same
       firm visibility rules as firm create/update.

  7) TOP MANAGEMENT (top_management) — reports oversight

2.7.0 Firm vs Network scope (REQUIRED)
--------------------------------------------------------------------
Two layers decide what firm-filtered work a user can touch:

  Layer 1 — ROLE + FIRM MEMBERSHIP (this section)
  Layer 2 — DELEGATED COMPLIANCE ACCESS multi-firm allowlist (§2.7.0a)
             (formerly UI label “Compliance check authority” — RENAME)

Roles unlock tools via Capabilities matrix UNION (§2.7.1). Firm membership
+ delegated access decide WHOSE firm data those tools reach.

Applies to: compliance queues (review / assign / change-status), reports,
activity logs / compliance audit trails, and other firm-filtered tools.

  A) MEMBER FIRM USER (users.firm_id → non-central firm, e.g. Firm1)
     - Baseline: own firm only.
     - PLUS every other firm that listed Firm1 (or this user’s firm) in
       its Delegated compliance access multi-select (§2.7.0a) — one-way.
     - Does NOT automatically see Central / Network or peer firms unless
       those firms delegated access TO Firm1.
     - Examples (caps permitting):
       • Approver Firm1 → Firm1 requests; also Firm3 if Firm3 checked Firm1.
       • Auditor Firm1 → Firm1 logs/trails (+ delegated firms’ trails).
       • Top Management Firm1 → Firm1 reports (+ delegated firms’ reports).
       • Manager Firm1 → assign / change-status for Firm1 (+ delegated).

  B) NETWORK / CENTRAL FIRM USER (users.firm_id → firms.is_central)
     - When they hold ANY of: `network_admin`, `top_management`, `auditor`,
       `accounts_admin`, or `approver` → hub-wide for those capability-gated
       tools (all member firms + Central / Network) — “network oversights
       the whole network”. Does NOT require each firm to check Central.
     - Examples:
       • Central Approver → all firms’ + network requests.
       • Central Auditor → all activity logs + audit trails.
       • Central Top Management → all firms’ / hub-wide reports.
     - Other Central roles (e.g. manager without an oversight role above,
       plain `user` / `advisor`) do NOT get automatic hub-wide bypass.
       They only see Central’s own work PLUS firms that checked
       Central / Network in Delegated compliance access (§2.7.0a).

  C) Control-plane bypass: power_admin, finproms_admin always bypass firm
     scope when their capabilities allow (ignore allowlist).

  D) Multi-role does NOT widen firm membership: Firm1 manager+approver
     still scoped as Firm1 (+ delegated). Central auditor+approver is
     hub-wide for both tools. Breadth of tools = role UNION.

2.7.0a Delegated compliance access (REQUIRED — rename + multi-firm)
--------------------------------------------------------------------
UI rename (Manage firms create/edit):
  OLD: “Compliance check authority”
  NEW: “Delegated compliance access”
  Help text: “Choose which firms (including Central / Network) may review,
  assign, see reports, and see audit trails for requests submitted by users
  of this firm. Access is one-way only.”

WHERE SET:
- On create / update of a firm (Manage firms). Capability:
  `dashboard_manage_firms` (unchanged gate).

UI CONTROL:
- Multi-select checklist of ALL other firms on the hub, INCLUDING the
  Central / Network firm (`firms.is_central`).
- Exclude the firm being edited (cannot delegate to self via this list;
  own-firm staff access is separate — see OWN FIRM below).
- ZERO or MORE firms may be checked (multiple peers + Central allowed).

MEANING (one-way):
- Settings live on the SUBJECT firm (the firm whose users submit work).
- Every CHECKED authority firm may work that subject firm’s compliance
  data — for staff of the authority firm who have the matching
  capabilities / roles (approver → review; manager → assign; auditor →
  audit trails; top_management → reports; etc.).
- NOT vice versa. Checking Firm2 on Firm1 does NOT let Firm1 touch Firm2.

EXAMPLE:
  Creating/updating Firm1 with Central / Network AND Firm2 checked:
  → Central / Network staff (within their caps; and Central oversight
    roles are already hub-wide per §2.7.0 B) and Firm2 staff may
    review, assign, see reports, and see audit trails for Firm1.
  → Firm1 staff still cannot review Firm2 or Central unless those firms
    separately list Firm1 on their own Delegated compliance access.

OWN FIRM:
- Staff of the subject firm always retain access to their OWN firm’s
  compliance work when their role/caps allow (legacy
  `compliance_visible_to_own`, default ON). Own firm is NOT removed by
  clearing the delegated multi-select.
- Optional: keep an explicit “Own firm staff” toggle if product still
  needs to hide own-firm queues; default ON.

RIGHTS GRANTED TO AUTHORITY FIRMS (when checked):
  For subject-firm submissions, authority-firm staff may (caps permitting):
  - Review / approve / reject / pick (approver caps)
  - Assign / unassign / change-status (manager / assign caps)
  - See compliance reports (report caps / top_management)
  - See compliance audit trails and related activity scoped to that firm
    (auditor / audit-trail caps)
  They do NOT gain Document Repository headship, Hub Users admin, or
  other non-compliance tools via this setting alone.

DATA MODEL (target — replace single peer):
- LEGACY: `compliance_visible_to_central` (bool) +
  `compliance_visible_to_firm_id` (single nullable FK).
- TARGET: many-to-many authorities, e.g. pivot
  `firm_compliance_authorities` (subject_firm_id, authority_firm_id)
  where authority_firm_id may be the Central firm OR any member firm.
  Keep `compliance_visible_to_own` (bool, default true).
- Migration: if `visible_to_central` was true → insert pivot row to
  Central firm; if `visible_to_firm_id` set → insert that peer row;
  drop or stop writing the old single-FK / central bool after backfill.
- API: accept `compliance_authority_firm_ids: number[]` (multi); expose
  the same on firm payloads. Keep legacy fields read-only during
  transition if needed, then remove.

SCENARIO MATRIX (caps assumed ON for the named role):

  | Actor                         | Sees Firm1 work?                                      |

SODs / MULTI-ROLE:

2.7.1 Multiple roles per user (REQUIRED change)
--------------------------------------------------------------------
Decision: YES — this change is approved and required. It is the correct
direction for the product: the Capabilities matrix is already role ×
capability; staff often need more than one hat (e.g. manager who also
approves). Doing this is FINE and recommended, provided the rules below
are followed so security and audit stay clear.

WHY THIS IS FINE:
- The matrix already models rights per role column; multi-role only changes
  how a user’s effective rights are computed (UNION), not the matrix itself.
- Modules remain functionality-flag based. Document Repository own-firm head
  rights are now ALSO expressed as system roles (`network_admin` /
  `firm_admin`) synced with `firms.head_user_id` — still firm-scoped, not
  hub-wide matrix ticks (§3.4).
- Risk is mainly migration + replacing “single `users.role`” assumptions in
  APIs, UI, imports, and audit display — not a redesign of the permission
  model.

CARDINALITY & STORAGE (target):
- User ↔ Role is many-to-many on each hub’s user store.
- Prefer a pivot (`user_roles`: user_id, role) OR an equivalent durable
  multi-value store. Do NOT keep only a single `users.role` column as the
  source of truth once multi-role ships.
- Migration: existing `users.role` becomes the user’s initial role; every
  current user gets exactly one pivot row matching today’s value.
- API: expose `roles: string[]` (and optionally `role_labels`). Keep legacy
  `role` as a privilege-ordered single-string mirror for old call sites /
  audit columns only — NOT a selectable “primary” role. Frontend must use
  multi-select assign UI and read `roles`. There is NO primary / secondary
  role concept; every assigned role is equal.

EQUAL ROLES (no primary / secondary):
- Each assigned role is a separate, equal role for that user.
- Do NOT label, select, or store a “primary” vs “secondary” role.
- When a single string is required (activity_logs.user_role, compliance
  audit actor role, uploaded_by_role, Excel single-cell fallback), derive
  a privilege-ordered legacy mirror automatically:
  power_admin > finproms_admin > client_admin > network_admin >
  firm_admin > top_management > accounts_admin > auditor > manager >
  approver > admin_staff > website_admin > advisor > user.
- That mirror does NOT limit capabilities and is NOT editable as “primary”.
- Capabilities always use the UNION of ALL assigned roles (below).
- UI badges / Hub → Users / Access Control show all role labels equally
  (chips or joined list) — no Primary badge or Primary role dropdown.

EFFECTIVE CAPABILITIES (UNION / OR):
- `userCan(hub, user, flag)` is TRUE if ANY of the user’s assigned roles
  has that flag checked on that hub’s §5.2 matrix (then apply existing
  module allow-list / acting-advisor / functionality gates as today).
- Dashboard nav / home cards = union of tools unlocked by any role.
- Admin-staff “act as advisor” continues to mirror the subject advisor’s
  effective capabilities when acting; having admin_staff among roles is
  what enables acting.
- Control-plane access: if the user holds `power_admin` among their roles,
  Central / pa_* rules apply as today for that role; other roles still
  contribute their hub matrix caps when acting on a content hub.

COMBINATION RULES:
- Any combination of non–control-plane roles is allowed
  (e.g. manager+approver, client_admin+approver, user+approver).
- `power_admin` MAY be combined with other roles only when explicitly
  assigned by a capable Power Admin; last-power_admin protection still
  applies (cannot remove the only power_admin on a connection).
- `finproms_admin` / `client_admin` may be combined with operational roles
  (manager, approver, …) so one person can admin and review.
- `network_admin` and `firm_admin` may be combined with other non–control-plane
  roles, but a user MUST NOT hold both `network_admin` and `firm_admin` at
  once (Central vs member-firm head are mutually exclusive). Firm membership
  must match the role (§2.7 / §3.4).
- Duplicate role keys on one user are ignored.
- Removing a role from a user is blocked if it would leave them with zero
  roles; the legacy `users.role` mirror is recomputed from remaining roles
  (privilege order above).

MANAGE ROLES / MATRIX COLUMNS:
- “Users per role” counts users who HOLD that role (a user with two roles
  appears in two column counts — expected).
- Delete role from hub matrix remains blocked while any user still holds
  that role (unchanged rule; multi-role makes this more important).
- Adding a custom / dormant system role to the hub is unchanged (§5.2).

USER MANAGEMENT & IMPORT:
- Hub → Users / Power Admin manage-users: role field becomes multi-select
  (assign / revoke roles only — no “set primary”).
- Advisor Excel import: Role column SHOULD accept one role (current) and,
  when multi-role is live, optionally a delimited list (e.g. manager|approver)
  or repeated role columns; imported set replaces only the roles specified
  for that row’s create path — document the chosen Excel format in the
  import template help text.
- Public self-register / plan subscribe: assign `user` only (do not wipe
  other roles if an existing account somehow already has more).

HARD-CODED ROLE CHECKS (must be updated):
- Any code that reads `$user->role === '…'` for authorisation MUST move to
  “user has role X” or “userCan(capability)” as appropriate.
- Approver-scoped list filters (e.g. hide view-all for pure approvers) must
  use role membership + capabilities, not a single string compare that
  breaks when approver+manager are combined — prefer capability-first;
  if a role-based exception remains, define whether “has approver AND has
  manager” uses the broader (manager) behaviour (RECOMMENDED: broader /
  union-friendly behaviour).

2.7.2 Separation of duties (multi-role conflicts) — REQUIRED
--------------------------------------------------------------------
When a user holds both submitter-style and reviewer-style roles (e.g.
advisor + approver, editor + approver, admin_staff + approver), capability
UNION must NOT allow them to decide on their own work.

CORE RULE (SMC / GC / WC):
- If the actor is the request OWNER (submitter / editor / subject advisor)
  OR the ON-BEHALF staff who created it, they MUST NOT:
  - appear in the assignable reviewers list for that request
  - self-assign or be assigned that request
  - review / approve / reject / approve-with-feedback
  - override status (manager change-status) on that request
- They MAY still see the item under “my / own” history and in hub-wide
  view-all / reports when those capabilities allow — viewing is not deciding.
- Admin-staff acting as advisor A: requests owned by A are conflicted for
  that staff while deciding; requests the staff submitted on behalf of anyone
  are also conflicted for that staff.

LIST / QUEUE BEHAVIOUR (SMC / GC — same pattern as Website Compliance):
- “Requests queue” (`unassigned_only`): new unassigned items with Pick it
  (and Assign for managers). Never include the actor’s own submissions.
- “All requests” (`history_only`): assigned / reviewed history. Approvers see
  their own assignments (`mine_as_approver`); managers with view-all / assign /
  change-status see hub-wide assigned history (firm-scoped). Own submissions
  stay under My requests only.
- Never offer self-assign / Pick it on conflicted own items.

REVIEWER LOOKUPS:
- Eligible reviewers = users who HOLD any role with the review capability
  (user_roles / multi-role), not the legacy users.role column alone.
- Always exclude conflicted user ids for the request being assigned.

TAXONOMY ADD REQUESTS:
- A user with taxonomy_request_add + taxonomy_request_manage must NOT
  approve or reject their own pending request.

OPTIONAL / LATER (document only unless product asks):
- Support ticket self-status-change block
- Self-affecting credit / plan changes requiring a second admin

IMPLEMENTATION: ComplianceSeparationService (backend) enforces the core
rule across SMC, GC, WC assign/review/status + reviewer lists + taxonomy.


2.7.3 Per-user capability overrides (REQUIRED)
--------------------------------------------------------------------
After the hub-wide role × capability matrix (§5.2) and multi-role UNION
(§2.7.1), staff may further refine capabilities for an individual user.

RULES:
- Candidate set = capabilities granted by ANY of the user’s assigned roles
  on that hub’s matrix (role UNION). The User capabilities UI shows ONLY
  those keys — check / uncheck within that set.
- Cannot GRANT a capability the user’s roles do not already have.
- Unchecking stores a denylist override (`users.capability_overrides` JSON:
  `{ "flag": false }`). Missing key = inherit role UNION.
- `userCan` = role UNION AND not denylisted AND existing module / acting /
  functionality gates.
- When roles are removed, overrides that no longer sit in the role UNION
  are pruned (activity: `user.capability_overrides_pruned`).

GATE / PAGE:
- Capability: `dashboard_manage_user_capabilities` (“Manage user capabilities”)
  in Hub operations — unlocks `/my-dashboard/user-capabilities`.
- APIs (hub_can): GET/PUT `/api/client-admin/user-capabilities/{userId}`
  (+ power-admin alias); GET list reuses hub-users listing under the same
  capability prefix.

ACTIVITY LOGS:
- Role matrix saves → `capabilities.role_matrix_updated` (enabled/disabled
  cells, including Power Admin `pa_*` column changes).
- Per-user saves → `user.capability_enabled` / `user.capability_disabled`.

IMPLEMENTATION: UserCapabilitiesService; wired in CapabilitiesMatrixService
  userCan; UserRolesService prune; AdminUserCapabilities frontend page.

3.3d Website Template Library vs Website Content Pre Approval Workflow
- Formerly one combined “Website Compliance” product. They are now TWO Modules
  checklist items. Content Pre Approval depends on Template Library.
- API namespace remains `/api/website-compliance/*` (shared tables); module and
  capability gates decide which half is available.
- Frontend dashboard shows TWO nav sections (not one “Website Compliance”
  umbrella): Website Template Library and Website Content Pre Approval.

  A) Website Template Library (`module_website_template_library`)
     - Showcase website templates only — no content pre-approval queue here.
     - Power Admin (if `wc_manage_templates`) adds / edits / deletes templates.
       When registering / editing a template, Power Admin can attach one or more
       colour schemes (name + primary + secondary) that suit that template;
       stored on `wc_templates.color_schemes` (JSON).
       Power Admin also defines the **available pages** for that template
       (name + slug + optional description) on `wc_templates.available_pages`
       (JSON). Requesters later select which of those pages to include.
     - Capable users browse the template catalogue.
     - Capable users request a template by filling the deployment form
       (`wc_request_deployments`) — domain, branding, colours, etc.
       On the request form they pick one of the template’s colour schemes, or
       enter an optional custom primary / secondary if none of the offered
       schemes fit. Chosen colours are saved on the template request as usual
       (`primary_color` / `secondary_color`).
       The request form also collects optional website content extras stored on
       `wc_template_requests`:
         • `services` — name + attached document (PDF/Office) list
         • `images` — uploaded image URL + optional label list
         • `contact_details` — phone, email, address, website
         • `policies` — name + attached document (PDF/Office) list
         • `selected_pages` — slugs chosen from the template’s `available_pages`
         • `page_contents` — document attachment (`url` + `name`) keyed by selected page slug
           (typed textareas are not used; attach a file for each page/service/policy)
     - Network Admin / Firm Admin request path (preferred):
       • Network Admin requests a website for their network (Central / Network
         firm); Firm Admin requests a website for their member firm.
       • Default caps ON for both roles: `wc_request_deployments` +
         `wc_assign_website_templates` + `wc_request_go_live`.
       • On create (and later re-assign), the form shows a multi-select of
         Website Admins (`website_admin` role). Eligibility uses the same
         Delegated compliance access rules as firm create/update (§2.7.0a) —
         API: `GET /api/website-compliance/website-admins`; body field
         `website_admin_ids: number[]` (legacy `assigned_advisor_id` still
         accepted as a single id).
       • MULTIPLE Website Admins may be assigned to ONE website
         (`wc_template_request_website_admins` pivot). First selected id is
         also stored on `assigned_advisor_id` as the primary content/cPanel
         owner for section scoping.
       • Website Admins edit content after deploy (`wc_edit_sections` /
         `wc_submit_change_requests` default ON for that role).
     - Website scope (`wc_template_requests.website_scope`) — read-only in UI:
       • `network` — requester is Network Admin (network website)
       • `firm` — requester is Firm Admin (firm website)
       • `independent` — requester is advisor / other self-serve (independent)
       • Set automatically on create from requester roles (never client-editable).
       • Shown as three disabled checkboxes (Network / Firm / Independent) on
         request, assign, deploy, go-live, and request-detail surfaces.
     - Request go-live (`wc_request_go_live`):
       • When a site is on staging and content work is complete, the original
         requester (Network Admin / Firm Admin / advisor who submitted the
         template request — `requested_by_id`) can ask Power Admin to deploy
         it to the main/live URL (`POST …/template-requests/{id}/request-go-live`).
       • Capability-gated: user must have `wc_request_go_live` AND be the
         original requester for that deployment. Defaults ON for
         network_admin, firm_admin, advisor, and manager.
       • Sets status → `ready_for_live`; Power Admin then promotes with
         `wc_deploy_websites`.
     - Power Admin (if `wc_deploy_websites`) manually deploys the pending
       request onto the respective cPanel (credentials + domain on deploy).
       Deploy is never automatic from the request form.
     - Related caps: `wc_view_all_deployments` (list), `wc_deploy_websites`
       (deploy / reject / promote go-live), `wc_assign_website_templates`
       (assign Website Admins), `wc_request_go_live` (requester go-live ask).
     - Capabilities in group “Website Template Library” are blurred while
       this module is off.

  B) Website Content Pre Approval Workflow (`module_website_compliance`)
     - Requires Website Template Library enabled (module dependency).
     - Full compliance flow on a deployed site’s sections.
     - Advisor / editor (if capable) locks/edits sections and submits change
       requests (`wc_edit_sections`, `wc_submit_change_requests`).
     - Approver / manager sees the whole flow: assign → review →
       approve & publish (status → published, immediate) OR approve only
       (status → approved, then schedule → scheduled → published) /
       reject / approve-with-feedback.
       Status overrides are blocked once published or scheduled.
       (`wc_assign_change_requests`, `wc_review_change_requests`,
       `wc_change_request_status`, `wc_view_all_change_requests`, …).
     - Optional bypass: publish live without review (`wc_publish_live_content`).
     - Supporting files: section 3.3c.
     - Capabilities in group “Website Content Pre Approval” are blurred while
       this module is off.

3.4 Document Repository (Firm Documents) — Network Admin / Firm Admin / Head
--------------------------------------------------------------------
Product name: Document Repository (UI / nav may say “Firm documents” /
“Documents”). Same module as today’s firm-scoped documents library.

- Firms already exist on hub databases (`firms` + `users.firm_id`; capability
  `dashboard_manage_firms`). Each hub has exactly ONE Central / Network firm
  (`firms.is_central = true`, default name “Central / Network”) plus any
  number of member firms.
- This section covers: designating heads via **roles** (preferred with
  multi-role) and/or Assign Head of Firm UI; and the firm-scoped Document
  Repository with per-member rights.
- Applies on Shared and White-labelled hubs (each hub’s own firms / members).
  Backend and frontend both required.

3.4.0 Functionality gate (hub-wide matrix only)
- Hub Functionalities checklist flag: `firm_documents` (“Firm documents” /
  Document Repository). Default OFF. Power Admin enables it per hub on
  Functionalities (often from Central Hub Controller → Hub Functionalities).
- While OFF, hub-wide firm-document Capabilities (view / add / delete /
  archive for ALL firms) are blurred / inactive on the Capabilities matrix.
- Network Admin / Firm Admin (Head of their firm) do NOT need this flag —
  holding the head role unlocks Document Repository for THAT firm immediately.
- Assign Head of Firm (`dashboard_assign_firm_head`) is NOT gated by this flag.
- Central control: toggling this flag on Central MUST sync to the content hub’s
  own database (remote DB wiring). Heads log into the content hub site
  (Shared / White-label), not Central — that hub’s API must have the same
  Document Repository / Head code deployed.

3.4.1 Who is Head — Network Admin vs Firm Admin (REQUIRED)
Two system roles designate firm heads (display names renameable per hub):

  A) NETWORK ADMIN (`network_admin`)
     - Head of the Central / Network firm only.
     - User MUST have `users.firm_id` = the hub’s central firm.
     - MULTIPLE Network Admins allowed per hub.

  B) FIRM ADMIN (`firm_admin`)
     - Head of the user’s own member firm (`users.firm_id`).
     - Example: member of Firm1 + role `firm_admin` → Head of Firm1.
     - MULTIPLE Firm Admins allowed per member firm.
     - Must NOT be used for the Central / Network firm (use `network_admin`).

Rules:
- A user MUST NOT hold both `network_admin` and `firm_admin` at once.
- Head designation is firm-scoped by membership — assigning `firm_admin` does
  not make someone head of a firm they do not belong to.
- Users may still hold other roles at the same time (multi-role UNION), e.g.
  advisor + firm_admin, manager + network_admin.
- Changing a user’s firm membership while they hold `network_admin` /
  `firm_admin` MUST either: move/clear headship consistently, or reject the
  firm change until the head role is revoked.

3.4.1a Appointing / syncing Head (two equivalent paths)
Either path designates Heads; both MUST stay in sync. Multiple admins OK:

  Path 1 — Update admins of this firm UI / API
  - Capability: `dashboard_assign_firm_head` (“Update admin of this firm”) —
    typically Power Admin / FinProms admin / Client admin as matrix allows.
  - Accepts `head_user_ids` (array of firm members). Empty array clears all
    admins for that firm.
  - MUST sync the matching role on each selected user (add) and revoke it
    from members no longer selected:
      central firm → `network_admin`
      member firm  → `firm_admin`
  - `firms.head_user_id` = optional primary contact (first selected / retained
    if still an admin). Not exclusive — Document rights use the role.

  Path 2 — Role assign (Hub → Users / multi-role UI / Excel when supported)
  - Assigning `network_admin` or `firm_admin` adds that user as an admin
    WITHOUT revoking other admins. Sets `head_user_id` only when currently
    empty (primary contact). Reject if firm membership does not qualify.
  - Revoking a head role from one user does not affect other admins; if that
    user was `head_user_id`, reassign primary to another remaining admin or
    clear it.

- `is_firm_head` / Document Repository unlock = user holds the matching head
  role with matching firm membership (preferred), OR is legacy
  `firms.head_user_id` / same-email primary contact.
- LEGACY: older “Head may be ANY role without network_admin/firm_admin” is
  superseded — new appointments always create/sync the head role. Existing
  heads without the role SHOULD be migrated (backfill `network_admin` /
  `firm_admin` from `head_user_id` + firm.is_central).

3.4.2 Head rights (own firm only) — Document Repository
- As soon as a user is Network Admin or Firm Admin (Head) for a firm, they
  unlock Document Repository in the dashboard and have ALL document rights
  for THEIR firm: add, view, delete, archive, granting those rights to firm
  members, and setting that firm’s visible-firms allowlist — no matrix tick
  and no Functionalities flag required for own-firm access.
- Documents are scoped to the firm. Network Admin’s own-firm scope is the
  Central / Network firm only (NOT automatic hub-wide access to every firm).
- Hub-wide access to ALL firms still requires §3.4.4 matrix caps
  (`firm_documents_view` / `_add` / …) on any role column (including the
  Network Admin / Firm Admin columns if Power Admin ticks them).
- Frontend unlocks via `firm_document_rights.is_firm_head` / merged
  `firm_documents_*` effective capabilities.

3.4.3 Head grants rights to firm members (per document)
- Member rights are PER DOCUMENT (not firm-wide for view/delete/archive).
- The Head (Network Admin or Firm Admin for that firm) opens access rights
  from a key icon on each document row; popup grants / revokes any
  combination of add / view / delete / archive for that document to members
  of THEIR firm. Members only receive what the head grants.
- Granting `can_add` on a document also unlocks firm-level upload for that member.
- Cleared when a user leaves the firm or is discontinued.

3.4.3a Folders / subfolders
- Documents may sit in a folder tree (folders + nested subfolders) scoped to
  the firm. On upload, choose an existing folder or create a new folder /
  subfolder. Library UI is a nested expand/collapse table of folders with
  documents inside; unfiled documents are listed separately.
- Upload new document control sits directly above the library table.

3.4.3b Categories (taxonomy, like GC content types)
- Hub-scoped document categories (`firm_document_categories`) with name/slug.
- Capability `firm_documents_manage_categories` (“Manage firm document
  categories”) — blurred while Functionalities → Firm documents is off.
  Same admin CRUD pattern as General Compliance content types.
- Upload form category dropdown lists these options (optional).
- Users without Manage can request a new category via `taxonomy_request_add`
  (see 3.4.3c); users with `taxonomy_request_manage` see the queue and
  approve/reject.

3.4.3c Taxonomy add requests
- Capability `taxonomy_request_add` (“Request new category / tag / type”) in
  Content catalog capabilities. One request capability covers:
  - SM Templates Library category or tag
  - Generic Compliance content type (GC module must be on)
  - Firm document category (Firm documents / Document Repository functionality
    must be on)
- Capability `taxonomy_request_manage` (“Manage taxonomy requests”) — see the
  queue. Reviewers create the option manually on the existing Manage
  categories / tags / GC content types / firm document categories pages,
  then mark the request Approved — or reject with a review note.
- Submit: proposed name + remarks. Statuses: Pending / Approved / Rejected.
- Dashboard nav: separate “Taxonomy requests” separator (Taxonomy requests /
  Request taxonomy / Taxonomy queue) — not under SM Template.
- APIs: `POST/GET /api/taxonomy-add-requests` (+ `/mine`, `/options`);
  admin `GET .../taxonomy-add-requests` + `POST .../approve|reject`
  under client-admin / power-admin / admin (gated by taxonomy_request_manage).

3.4.4 Capabilities matrix — hub-wide (all firms) + new role columns
- Matrix MUST include columns for `network_admin` and `firm_admin` (system
  roles; addable via Manage roles if dormant on a hub). Defaults for those
  columns: hub-wide `firm_documents_*` OFF (own-firm head rights come from
  the role itself, not these ticks). Other dashboard caps default OFF unless
  listed in §5.2 defaults for these roles.
- When Firm documents functionality is ON, these Capabilities are editable
  for EVERY role column (including Network Admin / Firm Admin):
  - `firm_documents_view` — view documents for ANY firm on the hub
  - `firm_documents_add` — upload documents for ANY firm on the hub
    (Head always has add for their own firm; not grantable via key icon)
  - `firm_documents_delete` — delete documents for ANY firm on the hub
  - `firm_documents_archive` — archive documents for ANY firm on the hub
  - `firm_documents_manage_access_rights` — key-icon access rights on
    documents for ANY firm (members + allowlisted firms). Head always has
    this for their own firm.
  - `firm_documents_manage_categories` — add/edit/delete category options
  - `firm_documents_manage_firm_access` — decide which firms may see a
    firm’s documents (allowlist). Blurred while Firm documents is off.
- These hub-wide admin tools are distinct from Head / member per-document
  grants. Ticking them on Network Admin does NOT replace Firm Admin rights
  on other firms unless the tick is hub-wide.

3.4.4a Visible firms + mixed access rights (every firm)
- Two-step model for ANY firm’s documents:
  1) Visible firms allowlist — Head of that firm (Network Admin for central /
     Firm Admin for member firms), OR any role with
     `firm_documents_manage_firm_access`, chooses which other firms may see
     that firm’s documents (`GET/PUT /api/firm-documents/visible-firms`).
  2) Per-document access rights (key icon) — lists OWN-firm users (3.4.3)
     PLUS only the allowlisted firms. Mode is `mixed`. Firm grants apply to
     every current member of the grantee firm.
- Recipient firm members see shared docs in their library under
  “Shared from other firms”.
- Removing a firm from the allowlist also clears its per-document firm grants.

3.4.5 Activity logs (required for the whole flow)
- Every mutation in this flow is written to `activity_logs` (same hub audit
  trail as section 6A). Suggested action keys:
  - `firm.head.assign` — Head of Firm appointed (include role key
    network_admin | firm_admin in payload)
  - `firm.head.replace` — Head of Firm replaced
  - `firm.head.clear` — Head of Firm cleared
  - `user.role_assigned` / `user.role_removed` — when headship is changed via
    multi-role assign (already logged by role service; correlate with firm id)
  - `firm.documents.member_rights.grant` — member document rights granted/updated
  - `firm.documents.member_rights.revoke` — member document rights revoked
  - `firm.documents.visible_firms.sync` — visible-firms allowlist updated
  - `firm.documents.firm_rights.grant` — firm-level doc access granted/updated
  - `firm.documents.firm_rights.revoke` — firm-level doc access revoked
  - `firm.documents.add` — document uploaded / created
  - `firm.documents.folder.create` — folder created
  - `firm.documents.view` — optional: record sensitive downloads if product
    requires audit of views (otherwise omit high-volume view noise)
  - `firm.documents.delete` — document permanently deleted
  - `firm.documents.archive` / `firm.documents.unarchive` — archive toggles
- Log payloads should identify firm id/name, actor, target user (for head /
  rights changes), head role key, grantee firm (for firm-level access),
  document id/name (for document actions), and granted rights flags — never
  store file binary contents; redact secrets.

4. WHITE-LABELLED HUBS (AND ADDITIONAL SHARED HUBS)
--------------------------------------------------------------------------------

4.1 Multi-instance / Same Codebase + Separate Databases
- Central Hub Controller is the registry and remote-control source.
- New Shared hubs and White-labelled hubs are created by copying/reusing the
  SAME codebase onto another cPanel (or hosting) — the same operational model
  previously described for Shared → White-label, now owned by Central Hub.
- There will be MANY white-labelled hubs (and optionally more than one Shared).
- Code must remain the SAME for Central Hub, Shared hub(s), and all
  White-labelled hubs.
- Each hub instance (Central, each Shared, every White-label) has its OWN
  database — not a shared multi-tenant DB. Content, users, and settings for a
  content hub live in that hub's database only.
- Everything that differs per hub (especially branding) must be driven by DB:
  - Application name
  - Colour scheme (primary / secondary / accent)
  - Logo
  - Public page content (Home / Posts·Reels catalog / post detail copy)
  - Dashboard menu labels (sidebar separators + menu item names)
  - Other tenant-specific settings as needed
- Hub settings are split into three capability-gated dashboard pages (same
  pattern as Privacy / Cookies):
  1) General settings — `dashboard_manage_settings`
     (`/my-dashboard/settings`, API GET/PUT `/client-admin/settings`):
     application name, from-email, NEW banner days, logos, favicon, auth
     background, colour scheme.
  2) Website content — `dashboard_manage_page_content`
     (`/my-dashboard/page-content`, API GET/PUT `/client-admin/page-content`):
     public Home / Posts·Reels catalog / post detail copy + footer powered-by
     logo upload. Import from another hub: GET
     `/client-admin/page-content/import-sources` + POST
     `/client-admin/page-content/import` `{ source_hub_id }` copies that hub’s
     page copy onto the current (acting) hub.
  3) Dashboard menu — `dashboard_manage_dashboard_nav`
     (`/my-dashboard/dashboard-menu`, API GET/PUT `/client-admin/dashboard-nav`):
     sidebar separators, menu item names, order, and grouping.
     Import from another hub: GET `/client-admin/dashboard-nav/import-sources`
     + POST `/client-admin/dashboard-nav/import` `{ source_hub_id }` copies that
     hub’s menu onto the current (acting) hub — useful when configuring many
     white-labelled hubs the same way.
  Values are returned on public GET /hub under branding / page_content /
  dashboard_nav and applied in the UI. Who may open each page is controlled
  independently on the Capabilities matrix.
- Page content is stored on `hubs.page_content` (JSON). Defaults live in
  `App\Support\PageContentDefaults`. Posts and Reels share one catalog page
  (`/posts?type=post|reel`) so catalog copy is shared, with separate
  title/lead/search strings where the type differs. Placeholders such as
  `{credits}`, `{date}`, `{count}`, `{year}`, and `{brand}` are substituted
  on the frontend.
- Public Home page (`/`) sections (all hubs; copy editable under Settings →
  Page content → Home):
  1) Hero — existing brand + title/lead/CTAs + post marquee (unchanged)
  2) Browse by Categories — top 8 hub categories by post count (hidden empty /
     catalog-off states); “View all” still opens the full catalog
  3) Website templates — always 3 showcase cards (left-aligned 3-column grid).
     Uses up to 3 distinct active hub templates; if fewer exist, the available
     template(s) are repeated to fill 3 boxes. Section omitted when none /
     WC module off (`GET /api/website-compliance/public/templates`)
  4) Support tickets — three tabs (Tickets / My tickets / Raise a ticket);
     wired to Support Tickets module + member ticket APIs when enabled
  5) Documents — promo layout with Read more → firm documents (or login);
     optional stacked image URLs from page_content
  6) Features — 4 cards (SM Templates / Canva / Website Compliance /
     Generic Compliance) with page_content copy + links
  Footer shows hub copyright (`footer_copyright` with `{year}`/`{brand}`)
  plus Powered by (`footer_powered_by_name`, optional `footer_powered_by_logo`
  image URL, optional `footer_powered_by_url` opening in a new tab).
  Public header shows hub brand plus editable `nav_tagline` (page_content home;
  blank hides the line) and site links (Home / Posts / Reels / Bundles / …).
  Categories use a left-aligned 4-column grid (max 8 cards); website templates
  always show 3 cards with the same hover-to-scroll preview as the dashboard
  template cards;
  documents section matches a two-column promo layout (category counts +
  carousel previews), ordering latest uploads first then most-used
  (category usage / attachment count).
- Dashboard menu labels are stored on `hubs.dashboard_nav` (JSON). Defaults live
  in `App\Support\DashboardNavDefaults`. Separators include context-specific
  Hub labels (Central / Shared / White-labelled). Menu items are keyed by path.
  Settings also control separator order (`section_order`), which separator each
  item sits under (`item_groups`), item order (`item_order`), and custom
  separators (`custom_*` keys in `sections` / `section_order`).
- Power Admin on CENTRAL HUB CONTROLLER is the control plane. The Central Hub
  DB stores a hub registry for every Shared and White-label hub, including
  deploy wiring so Central can reach that hub for management / content push:
  - hub_type — shared | white_label (and optionally central for the controller)
  - frontend_url — public site URL for that hub's deploy
  - api_url — optional backend API base URL
  - db_* — that hub's database connection (host, port, database, username,
    encrypted password, driver) so Central can push content / sync / act remotely
  - deploy_notes — free-text ops notes
  - Deploy contract: each content-hub deploy uses the SAME codebase with its OWN
    .env (its own DB_* + FRONTEND_URL / APP_URL). HUB_SLUG identifies the hub
    on that deploy. Central does NOT share the content hub's database.
  - When frontend_url is set, emails / Stripe return URLs prefer that hub URL
    over the global FRONTEND_URL env (on that hub's own deploy).
  - Power Admin hub detail shows a deploy checklist + copyable env snippet.
  - Hub detail is registry / deploy wiring only — Functionalities, Modules,
    Capabilities, and Subscriber credits are managed after selecting the hub
    in the Control hub switcher (not via boxes on hub detail).
  - When Central acts on a Shared/White-label hub, relative post/bundle media
    paths are resolved against that hub’s api_url / frontend_url media base
    (not Central’s APP_URL), so Shared catalog images load in the dashboard.
    Registry "ready" = active + frontend_url + remote DB credentials set.
  - Hub list badges: Wiring ready / Needs wiring.
- Content push / remote acting (Central → Shared or White-label): Power Admin
  (and other roles with capability, if enabled) select target hub(s); Central
  uses the stored remote DB connection (or API) to publish into / act on that
  hub's own database.

4.2 Private Access (White-labelled)
- White-labelled hubs are PRIVATE.
- Public users cannot subscribe.
- Client provides an Excel sheet of advisors.
- Advisors from that sheet are added into the application.
- Power Admin (on Central Hub) sets subscriber credits for the hub
  (dashboard + Capabilities):
  - Capability: `dashboard_manage_subscriber_credits` (private-hub dashboard tool)
  - Unlimited (default for white-label), OR
  - A fixed number of credits per subscriber per billing period.
- On Excel import, each new / reactivated advisor receives that allotment
  (unlimited flag, or balance set to the hub credit number).
- If Power Admin changes the credit number (or switches unlimited ↔ fixed)
  after advisors are already subscribed, existing balances are NOT changed
  mid-period; the new allotment is applied on the next monthly autorenew
  to all active advisors.
- Client admin (or Power Admin with import capability) can Discontinue an
  individual advisor: permanent end of access (WP FPSUB end equivalent).
  Discontinued advisors cannot log in, drop out of billing counts, and are
  not restored when the hub flips private again. Re-importing the same email
  restores them. Gated by Capabilities matrix key `advisor_discontinue`.
  Discontinue is shown on Hub → Users (`/my-dashboard/hub-users`), not on
  Import Users.
- Import Users page (`/my-dashboard/advisors`):
  - Users with `advisor_excel_template` (or Import / Submit) can download the blank
    Excel template, fill it offline.
  - Users with `advisor_excel_submit` upload the filled sheet; it is stored as
    Pending in import history with the user count, waiting for an importer.
  - Users with `advisor_excel_import` can import immediately or process a Pending
    submission from history.
  - Users with `advisor_excel_view_submissions` (or Import) can see ALL submitted
    Excel sheets in history with full details and download the stored filled file
    while it remains on disk (Pending until imported / pruned). Roles with only
    Submit see their own submissions; other people’s submissions are hidden.
  - History lists prior imports and pending submissions (who sent, when, file,
    user count / created / updated / skipped).
- When Power Admin switches a hub from private → public (Functionalities):
  - All Excel-imported advisors are SUSPENDED (not deleted): cannot log in,
    lose unlimited/subscription access, excluded from advisor billing counts.
  - Advisor Stripe auto-renew is canceled; pending advisor billings are canceled.
  - Private-related functionalities are turned off and public ones turned on
    (paid credits, one-off purchase, public subscribe; unlimited credits and
    advisor subscriber billing off).
- When the hub is switched back public → private:
  - Previously suspended imported advisors are REACTIVATED with the hub’s
    current subscriber-credit allotment and advisor_import subscriptions restored.
  - Auto-renew is NOT restarted automatically; client admin pays again after
    import / billing flow if needed.

4.3 Module recurring pricing for White-labelled (replaces advisor rate tiers)
- Advisor pricing tiers are RETIRED. Recurring charges use module catalogue +
  slot tables (editable under Modules → Module prices).
- Functionality: `charge_recurring_per_module` (default ON white-label / OFF shared).
- Slot tables (#1 SMTL, #2 SMC, #3 GC) by active user headcount bands
  (0–100 / 101–250 / 251–500 / 501+). Rate + network margin per band.
- Import Option B: rate from TOTAL active users with that module (not suspended,
  not discontinued); invoice charges RATE × THIS IMPORT BATCH only; due today.
- Same batch renews monthly on the import anniversary day (active users only).
- Renew day (`/my-dashboard/advisor-renewal`): charge hub payment card for ALL
  due unpaid invoices (one-time + recurring). Grace day (≥ renew day): after
  grace, unpaid recurring seat invoices suspend those users; unpaid one-time
  module invoices disable those modules.
- Discontinue (`advisor_discontinue`) applies to ANY hub user (not only advisors);
  discontinued users are excluded from future recurring seat counts.

4.4 Remote control of content hubs (from Central Hub Controller)
- Capability: `dashboard_control_white_label_hubs` — “Control hubs remotely”
  (name may be generalized to cover Shared + White-label; replaces the old
  per-form Hub dropdown / `dashboard_push_content`).
- Users with this capability on CENTRAL HUB (typically Power Admin) get a hub
  switcher at the top of the Central Hub dashboard.
- Selecting Central Hub context → platform tools only (registry, checklists, etc.).
- Selecting a Shared or White-label hub → dashboard menus/tools follow THAT
  hub’s Capabilities matrix for the user’s role (e.g. View posts). Authenticated
  GET /hub also overlays that hub’s `dashboard_nav` (sidebar separators + menu
  item names from Settings) so Central’s menu labels match the selected hub.
  Creating posts / types / categories / tags is Central-only (Central content
  library); while a content hub is selected those pages are list-only. Bundles
  and other hub tools still write to THAT hub’s own database when enabled.
- Dashboard “Website” / “Back to website” always opens THIS deploy’s public
  site (`/`), gated by `member_view_site_pages` on the control-plane (Central)
  matrix for that user. It must NOT open the selected Shared / White-label
  `frontend_url` (cross-origin login caused flicker → blank screen).
  Power Admin / FinProms Admin cells for `member_view_site_pages` always
  read/save on Central (even while the hub switcher is on a content hub), so
  enabling the capability turns on the Central Website button.
- APIs: `GET/PUT /client-admin/acting-hub` (and power-admin / admin aliases).
  Authenticated `GET /hub` includes `hub_switcher` + acting effective caps when
  on Central Hub with remote-control capability.
- Target hub for the switcher must be active with remote DB credentials
  configured on the Central Hub registry (deploy wiring). Selecting a hub for
  remote control does NOT require “Receive content from Central Hub”.
- “Receive content from Central Hub” (`receive_content_from_shared`) only gates
  Central content library distribute / content push — not the hub switcher.
- Central content library (capability `dashboard_central_content_library`,
  Central Hub only):
  - Create manual posts one-by-one or bulk Excel (template download like
    advisor import). Posts remain in the Central DB.
  - AI posts tab is under development (empty stub).
  - Distribute non-archived (ready) library posts to Shared / White-labelled
    hubs. Copies are inserted into the target hub DB. Re-distributing a post
    to a hub that already has it (tracked via content_pushes + remote row)
    skips the insert — no duplicate. Archive is optional:
    it retires a post from the distribute pool with required remarks but does
    not delete or hide it from the Central library list. Unarchive clears
    remarks and restores the post to the distribute pool.
  - Central posts list lives on `/my-dashboard/posts` (ready + archived, with
    search/filters and “published on” hubs). Editing a Central post also
    updates the copies on hubs it was successfully distributed to.
  - Central library page tabs: Create / AI posts / Distribute / Archive
    (archive / unarchive is its own tab, not nested under Distribute).
  - Distribution checks: non-archived posts only; AI posts only to hubs with
    `ai_posts`; manual posts only to hubs with `manual_posts`.
  - Target hubs list includes every active Shared and White-labelled registry
    hub. Selectable (eligible) hubs need Receive content from Central, remote
    DB wiring, Social Media Template Library, and Manual or AI posts. Ineligible
    hubs stay visible but disabled with a reason. White-label hubs default to
    receive + manual posts (same as Shared).
  - Types / categories / tags with Central library:
    - Central keeps its own taxonomy tables (`content_types`, `categories`,
      `tags`) plus type/categories/tags names stored on each Central post.
    - On create (one-by-one or Excel), Central upserts any new type /
      category / tag names into Central’s own taxonomy tables so the library
      form and Manage types/categories/tags stay in sync.
    - The Central library create form accepts existing names or new free-text
      names; Manage types / categories / tags pages on Central remain the
      full CRUD admin for Central taxonomy.
    - On distribute, the push upserts by **name** into the target hub’s own
      DB: any type, category, and tag used on the Central post is created on
      the target if missing (or refreshed if a matching name already exists),
      then the post copy is inserted with the same type/categories/tags values.
    - Central Manage categories create/update/delete also syncs immediately to
      every eligible content hub (Receive content from Central + remote DB
      wired): name/slug/icons upsert; renames rewrite remote post category
      lists; deletes remove unused remote rows. Soft-fails per hub so Central
      CRUD always succeeds; response includes `hub_sync` summary.
    - This is a copy/upsert, not a live link back to Central. Each Shared /
      White-label hub keeps its own taxonomy tables; local-only types/
      categories/tags on a hub are left alone unless a distributed post
      carries that name (or Central category sync upserts that name).
    - While the hub switcher is on a Shared / White-label hub, Manage types /
      categories / tags writes only to THAT hub’s DB (for local catalog work),
      not Central’s.
    - Public member catalog taxonomy GETs (`/types`, `/categories`, `/tags`)
      require `member_browse_catalog` OR (when authenticated) Central library /
      manage-types/categories/tags capabilities — Central keeps member catalog
      off, so Power Admin still loads taxonomy for the Central library form
      via the dashboard capability OR.
- Media for remote posts is stored as a public URL reachable from Central /
  source storage (file uploaded via controlling instance, path saved on the
  target hub DB).
- While a target hub is selected, list/create/update/delete that hub’s content
  via the normal dashboard endpoints (`/posts`, `/types`, `/categories`, `/tags`,
  `/bundles`) or `/hub-content/...` — both use the acting hub (no `hub_id`).
  IDs in those requests are remote hub database IDs.
- Shared Hub no longer hosts this cross-hub control plane for itself + others;
  that responsibility moves to Central Hub Controller.

4.5 Code Updates
- Updates made in the master codebase are reflected on Central Hub, Shared
  hub(s), and White-labelled hubs (same codebase / deploy model). Deploy each
  instance when releasing.

5. RIGHTS / PERMISSIONS CHECKLISTS (CRITICAL)
--------------------------------------------------------------------------------
- Because Central, Shared, and White-labelled use the SAME code, behaviour
  differences must be gated by checklists (feature flags / rights), not
  hard-coded forks.
- Power Admin manages these checklists from the CENTRAL HUB CONTROLLER
  Power Admin dashboard, for EACH Shared hub AND EACH White-labelled hub.
- Opposite options (e.g. public vs private, paid vs unlimited credits, manual posts
  vs AI posts) must be mutually exclusive: checking one auto-unchecks the other.

5.1 Hub Functionalities checklist (Power Admin → Functionalities)
- Formerly "hub behaviour". Controls how the hub works for that tenant, e.g.:
  - Public subscribe / self-registration vs private invite-only
  - Paid credits vs unlimited credits
  - One-off purchase for non-subscribers
  - Receive content from Central Hub (legacy name may still say "from shared")
  - Manual posts vs AI posts (opposites — checking one unchecks the other).
    Controls which Central library posts this hub may receive on distribute
    (manual → Manual posts hubs; AI → AI posts hubs). Default: Manual on.
  - Advisor subscriber billing (rate × advisors)
  - Charge amount per module (one time) — `charge_amount_per_module`
    - Default ON for white-labelled hubs; OFF for Shared hub(s); N/A or OFF
      for Central Hub Controller itself
    - When ON, enabling a billable product module generates a one-time invoice
      at the configured catalogue price (see 5.1B)
  - Support Tickets — `support_tickets` (default OFF). When on, Support Tickets
    capabilities (`st_*`) become available on the matrix (section 3.3e). Not a
    Modules-page product module.
  -   Live Chat — `live_chat` (default OFF). When on, Live Chat capabilities
    (`lc_*`) become available on the matrix (section 3.3d2). Shared / WL hubs
    choose Central contacts via their own checkbox page. Not a Modules-page
    product module.
  - Security Monitoring — `security_monitoring` (default OFF). When on, Security
    Monitoring capabilities (`secmon_*`) become available on the matrix
    (sections 3.3f / 6F). Separate feature module for regular security
    monitoring + incident reports; NOT a Modules-page billable packaging module.
- Each content hub (each Shared + each White-label) has its own configuration.
- Edited ONLY from Hub Functionalities / hub checklist screens on Central Hub
  — not from the Capabilities matrix (no duplication).
- After Functionalities / Modules / Capabilities are saved for a hub, the
  frontend must refresh hub context (with a dashboard loader) so the navbar
  updates to match the new checklist and effective capabilities.

5.1A Modules checklist (Power Admin → Modules, same hub checklist screen)
- Per-hub module toggles (functionality group `modules`):
  - Shared Hub / White Label Hub — locked base packaging module for hub type
  - Social Media Template Library — posts / reels catalog
  - Social Media Pre Approval Workflow — activates SMC capability section
    (capabilities blurred while this module is off)
  - Website Template Library — templates catalogue, request form, manual
    cPanel deploy (section 3.3d-A); activates WTL capability section
  - Website Content Pre Approval Workflow — section edit + change-request
    approval flow (section 3.3d-B); requires WTL; activates WC capability section
    (capabilities blurred while this module is off)
  - Generic Content Pre Approval Workflow — activates GC capability section
    (capabilities blurred while this module is off)
- Module packages (see 5.1C): optional bundles of Shared/White Label Hub and/or
  the 5 product modules with a single package price. Product modules covered by
  an enabled package are locked on this screen (`locked_reason=module_package`)
  and cannot be toggled separately; hub base stays type-locked but is covered
  for billing when included in the package.
- Managed via `dashboard_manage_modules` / Modules API on Central Hub.
- When `charge_amount_per_module` is ON, newly enabling a module (including
  uncheck → check again) creates a one-time invoice. Previous enable invoices
  for that module are deleted so only the new enable invoice remains. £0
  catalogue prices still create a paid/complimentary invoice. Website Template
  Library (`billing_unit=per_website`) creates ONE enable invoice for currently
  deployed website template requests (`wc_template_requests`, unit rate × count)
  — not the showcase catalogue (`wc_templates`). New deployments also create a
  per-request one-time invoice when WTL uses per_website. Recurring WTL uses the
  same deployed request count. Invoices-page backfill does not duplicate enable
  invoices.

5.1B Module catalogue pricing (Modules pricing)
- Official default catalogue (editable via capability / database):
  One-time:
  1) Shared Hub / White Label Hub — £14,500 per network
  2) Social Media Template Library — £0 per network (included; invoice still created, auto-paid)
  3) Social Media Pre Approval Workflow — £5,000 per network
  4) Website Template Library — £300 × deployed website template requests
     (wc_template_requests) on enable; new deploys also invoice per request —
     NOT the template showcase catalogue (wc_templates)
  5) Website Content Pre Approval Workflow — £10,000 per network
  6) Generic Content Pre Approval Workflow — £3,500 per network
  Recurring (functionality `charge_recurring_per_module`):
  1) Shared / White Label Hub — £4,500 per network / month
  2) Social Media Template Library — slot #1 per user (slots) / month
  3) Social Media Pre Approval — slot #2 per user (slots) / month
  4) Website Template Library — £125 per website request / month
  5) Website Content Pre Approval — £1,500 per firm / month
  6) Generic Content Pre Approval — slot #3 per user (slots) / month
- Billing units (SAME dropdown for one-time `billing_unit` and ongoing
  `recurring_billing_unit` on modules AND packages; recurring also allows `none`):
  1) per_network — Invoice per the network / central firm (usually one). Flat × 1.
  2) per_firm — Invoice generated per firm on the hub (amount × firm count).
  3) per_user — Invoice generated per user at a FIXED catalogue rate
     (amount × active users with the module / any package module). No tier table.
  4) per_user_slots — User-count slots define the rate from
     `module_recurring_tiers` (any slot number; create new slots freely);
     invoice uses that slot rate × billed users (import / anniversary batches
     for ongoing; enable qty × slot rate for one-time).
  5) per_website — Per website template request (deployed wc_template_requests),
     not the template showcase catalogue.
  Legacy codes still accepted then normalized: `one_time` → per_network;
  `per_adviser` → per_user_slots.
- Stored in `module_pricing` (+ recurring_* columns) and `module_recurring_tiers`.
- Capabilities group “Modules pricing” (blurred while BOTH charge flags off):
  - `dashboard_manage_module_pricing` — Set one-time + recurring catalogue / slots
    for modules that apply to the current hub type only (Shared base + products
    on Shared; White Label base + products on WL; Central base on Central)
  - `dashboard_manage_module_packages` — Create/edit/delete module packages
    (bundled Shared/WL Hub and/or product modules with their own one-time +
    recurring package price); separate page `/my-dashboard/module-packages`
  - `dashboard_view_module_invoices` — Who can see module invoices
  - `dashboard_mark_module_invoices_paid` — Manually mark unpaid module invoices paid
- APIs: GET/PUT module-pricing (filtered by hub type; returns `billing_units` +
  `recurring_billing_units` option lists with labels/descriptions);
  POST/PUT/DELETE module-recurring-tiers (CRUD for slot bands: any slot
  number 1–255, min/max users, rate, network margin; create a new slot by
  posting a tier with a new slot number);
  GET/POST/PUT/DELETE module-packages (same unit option lists; capability-gated);
  module-invoices…
- Invoice types: `module_billing` (one_time), `module_recurring` (recurring)
- Scheduler: `billing:process-module-cycles` daily — anniversary invoices, renew-day
  card collection, grace penalties
- Frontend: Module prices / packages show the same unit dropdown for one-time and
  ongoing; show slot picker when unit is per_user_slots; advisor-pricing page
  removed from nav (tiers retired); Billing renew + grace page under Advisors

5.1B2 Module invoice / payment settings (who pays) + separated invoice pages
- Page `/my-dashboard/module-invoice-settings` gated by
  `dashboard_manage_module_invoice_settings`.
- Capabilities (grantable to any role; firm/reseller caps inactive while the
  matching invoice setting is off):
  - `dashboard_manage_network_payment_card` — network tab on Payment card
  - `dashboard_manage_firm_payment_card` — firm tab (needs firms_pay_own)
  - `dashboard_view_network_module_invoices` — Module invoices (network payer)
  - `dashboard_view_firm_module_invoices` — Module invoices (firm payer)
  - `dashboard_view_reseller_invoices` — Reseller invoices page (menu when granted;
    list fills when network_resells is on)
  - `dashboard_manage_reseller_module_pricing` — Reseller module prices page
    (per_user / per_user_slots only; edit when network_resells)
  - `dashboard_manage_network_stripe` — Network Stripe keys page
    (save when network_resells)
  - `dashboard_mark_module_invoices_paid` — settle network/firm module invoices
  - Personal card: NO capability — My payment method (mandatory if users_pay_own OR network_resells)
- Pages:
  - `/my-dashboard/payment-card` — network and/or firm cards (tabs)
  - `/my-dashboard/my-payment-method` — personal card (shown if users_pay_own or network_resells)
  - `/my-dashboard/module-invoices` — network/firm one-time + recurring only
  - `/my-dashboard/my-invoices` — personal + user-billed module invoices
  - `/my-dashboard/reseller-invoices` — network→user charges (admins)
  - `/my-dashboard/reseller-module-pricing` — amounts users pay the network
    (only modules whose main Module prices unit is per_user / per_user_slots;
    network still pays FinProms at main Module prices)
  - `/my-dashboard/network-stripe` — network Stripe publishable/secret/webhook
    for user payments under network_resells
  - `/my-dashboard/one-time-invoices` — ALL one-time invoices (who pays ignored)
  - `/my-dashboard/advisor-invoices` — label “Import users invoices”
- Intelligent sync on save (enables only): network → network card + view;
  firms_pay_own → firm card + firm view; network_resells → reseller view.
  users_pay_own / network_resells do not grant caps (My payment method + My invoices).
- Per-hub settings (`hub_module_invoice_settings`):
  1) `network_pays_all` — Network pays ALL module invoices (every pricing unit,
     one-time + ongoing). Checking this clears firm + user options.
  2) `firms_pay_own` — Each firm pays its own invoice when the unit is
     `per_firm` (one invoice created per firm). Other units remain paid by
     the network.
  3) `users_pay_own` — Each user pays their own invoice to the network/platform
     when the unit is `per_user` / `per_user_slots`. Personal card mandatory
     (My payment method). Other units remain paid by the network.
  4) `network_resells` — Network pays the platform for all invoices, then may
     re-charge users with its own pricing (user pays the hub). Checking this
     clears `users_pay_own`. Personal card still mandatory for each user.

6B. HUB BACKUP & RESTORE
--------------------------------------------------------------------------------
- Dual storage (content hubs): each scheduled/manual backup is saved on the hub's
  own server (storage/app/backups/{slug}/) AND a copy is stored on Central
  (storage/app/backups/central/{slug}/).
- Central Hub backs itself up once on the same server
  (storage/app/backups/central/{slug}/ only — no local+central duplicate).
  Power Admin can download / restore. Prefer a true off-server copy for DR.
- Schedule is per hub, set from Central (Power Admin + pa_manage_hub_backups):
  enabled, time (HH:MM), timezone, daily|weekly (+ weekday), retention local /
  Central. Settings sync to content hubs via remote DB push when wired.
- Scheduler: `hubs:run-due-backups` every minute (requires schedule:run cron on
  each deploy). Central also triggers due remotes via hub api_url when set.
- Restore from Central uses the Central-stored zip; content hubs receive the
  archive on POST /api/internal/hub-backups/restore (**X-Hub-Restore-Key**,
  not the backup key).
- Purpose-scoped machine auth (2026-10-21): compromising backup credentials
  MUST NOT authorize restore, GC file bridge, or deploy-env writes.
    - run / receive → `X-Hub-Backup-Key` + `backup_token` / `HUB_BACKUP_SECRET`
    - restore → `X-Hub-Restore-Key` + `restore_token` / `HUB_RESTORE_SECRET`
    - GC files → `X-Hub-Gc-File-Key` + `gc_file_token` / `HUB_GC_FILE_SECRET`
    - deploy-env → `X-Hub-Deploy-Env-Key` + `deploy_env_token` / `HUB_DEPLOY_ENV_SECRET`
    - code updates remain on `X-Hub-Code-Update-Key` + `code_update_token`
  Saving backup schedule mints all purpose tokens; WhiteLabel sync pushes them
  to content hubs. Optional `HUB_INTERNAL_ALLOWED_IPS`; throttle
  `internal-hub` + stricter `internal-restore`.
- Env (optional): CENTRAL_API_URL on content hubs for independent upload;
  purpose-scoped shared secret fallbacks (never reuse one value for all);
  per-hub tokens auto-generated.
- Capability: pa_manage_hub_backups (Power Admin platform checklist).
- **Encryption at rest (NFR-BACKUP-ENC):** completed ZIP archives are encrypted
  on disk with streaming AES-256-GCM (`HBENC1` header) when
  `HUB_BACKUP_ENCRYPT_AT_REST=true` (default). Prefer a shared
  `HUB_BACKUP_ENCRYPTION_KEY` (base64 32-byte) on Central **and** every content
  hub so dual-store upload / Central download / remote restore can decrypt.
  Without that key, a key derived from local `APP_KEY` is used (single-server
  only). Legacy plaintext archives still restore/download. Download API decrypts
  to a normal ZIP for the admin. `hub_backups.is_encrypted` records status.
  Does not rewrite historical dumps per GDPR erasure (still residual for old
  plaintext files until rotated by retention).

6B.1 MODULE DISASTER RECOVERY AND ROLLBACK (VIA SECURITY MONITORING)
--------------------------------------------------------------------------------
Status: IMPLEMENTED (2026-10-16) — backend + frontend.
Cross-refs: section 6F (Security Monitoring — detection), NFR-AVAIL (9.9),
§6B (whole-hub backup — DIFFERENT tool), §1C (code release apply — DIFFERENT).

Purpose (NOT the same as Security Monitoring alone, NOT whole-hub restore)
- Security Monitoring (6F) RECOGNIZES / detects the disaster (events → incident).
- Module disaster recovery then recovers by rolling back ONLY the affected
  product module’s data to a prior module snapshot.
- Does NOT restore the whole hub database/code (§6B Restore).
- Does NOT re-apply full release zips (§1C) — that is deploy rollback, not
  module disaster recovery.

Lifecycle
  1) Detect — automated or manual security incident (6F).
  2) Recognize disaster — attach `affected_module` (product module key) and
     set `disaster_recognized`. High/critical auto-incidents infer module from
     route/event when possible and auto-recognize.
  3) Snapshot — module-scoped JSON snapshot of that module’s tables (+ checklist
     flag). Operators can create snapshots anytime; recognition creates a
     baseline if none exists.
  4) Roll back — restore ONLY that module’s tables from a chosen snapshot.
     A pre-rollback safety snapshot of current module state is taken first.

Recoverable modules (v1)
  - module_general_compliance
  - module_social_media_compliance
  - module_website_compliance
  - module_website_template_library
  - module_social_media_template_library

Capability
  - `secmon_manage_disaster_recovery` (Security Monitoring group; blurred while
    Functionalities → security_monitoring is off). Defaults ON for hub-admin
    roles like other secmon_* manage caps.

APIs (hub_can; also under /power-admin/* when acting)
  - GET  …/security-monitoring/disaster-recovery/modules
  - GET  …/security-monitoring/disaster-recovery/snapshots?module=
  - POST …/security-monitoring/disaster-recovery/snapshots
        { module_key, label?, security_incident_id? }
  - POST …/security-monitoring/incidents/{id}/recognize-disaster
        { affected_module }
  - POST …/security-monitoring/incidents/{id}/rollback
        { snapshot_id }
  - Declare incident accepts optional affected_module + recognize_disaster.

UI (Security Monitoring → Incidents)
  - Declare: optional affected module + “Recognize as module disaster”.
  - Incident detail: Disaster recovery panel — recognize, create snapshot,
    select snapshot, Roll back module.
  - Incident list shows affected module + Disaster badge when recognized.

Storage
  - Table `module_disaster_snapshots` + payload files under
    storage/app/module-disaster-snapshots/{hub_id}/{module}/…
  - Incident columns: affected_module, disaster_recognized,
    disaster_recognized_at, recovery_status, last_snapshot_id,
    last_rollback_snapshot_id, last_rollback_at.

Explicit non-goals (v1)
  - Whole-hub restore (use §6B)
  - Full codebase rollback (use §1C release apply of a prior package)
  - Multi-region failover / PITR beyond module snapshots

Acceptance criteria
  [x] Documented here + NFR-AVAIL 9.9 + §8 checklist; distinct from 6F detect-only
  [x] Capability + APIs + Security Monitoring UI
  [x] Snapshot + rollback restores only the chosen module’s tables
  [x] Feature tests for recognize/rollback (GC) + capability gate

Cross-refs: section 6F (Security Monitoring — related but NOT the same),

Purpose of this section (combined product requirement)
- “Activity logging and anomaly detection” is ONE product area with TWO parts:
  1) Activity logging — record and report what users/APIs did (audit trail)
  2) Anomaly detection — flag unusual patterns derived from that trail
- Part 1 is already live. Part 2 is a new submodule under Activity Logs
  (same nav area / capability family), not a replacement for Security

How this relates to Security Monitoring (6F) — READ THIS
- Activity Logs (6A) and Security Monitoring (6F) are NOT the same module.
- Activity Logs = general audit of product usage and mutations (“who did what”).
- Security Monitoring = dedicated security-threat / incident module (events,
  incidents, thresholds, “Monitor now”, secmon_* caps, `security_monitoring`
  Functionality flag). It already detects some security anomalies (e.g.
  repeated failed logins, rate-limit trips) into `security_events`.

6A.2 Anomaly detection (Activity Logs submodule)
--------------------------------------------------------------------------------
Status: IMPLEMENTED (backend + frontend) — Activity Logs → Anomaly detection tab;
APIs under /activity-logs/anomalies*; artisan `activity:detect-anomalies`
every 15 minutes + near-real-time hooks after selected activity_log writes.

Goal
- Add an **Anomaly detection** module/surface under Activity Logs that reviews
  `activity_logs` (and related signals) and surfaces unusual patterns so
  capable users can see: when it looked abnormal, what pattern matched, who /
  what was involved, and current review status.
- This is the missing half of “Activity logging and anomaly detection”.
  Logging alone does not equal anomaly detection.

Scope (v1 — activity-pattern anomalies)
  Minimum detector set (configurable thresholds where noted):
  A) Auth / access patterns from activity_logs
     - Unusual login volume for a user or IP vs recent baseline
     - Logins from a new / rare IP or user-agent for an established user
     - Burst of failed / blocked login actions in a short window
       (complement 6F failed-login threshold; may link to existing secmon event)
  B) Privilege / admin actions
     - Spike in high-impact actions (capabilities change, user suspend /
       discontinue, force-logout, GDPR export/erase, secrets/settings mutate)
     - Same actor performing many distinct admin actions in a short window
  C) Data / export volume
     - Unusual download / export / report-view volume from one user
  D) API / mutation volume
     - User or IP far above their own recent action-rate baseline
  Out of scope for 6A.2 v1 (already owned by 6F / NFR-SEC-*):
     - Dependency vulnerability scans (“Monitor now”)
     - Malware / upload firewall gates (NFR-SEC-FW)
     - Full incident lifecycle UI (acknowledge → investigate → resolve) —
       prefer linking to Security Monitoring incidents when security-relevant
     - Network IDS / SIEM replacement

Enablement & permissions
- Lives under the existing Activity Logs product area (same nav parent).
- Default gate: same capability `dashboard_view_activity_logs` for viewing
  anomaly feed / summary (keeps one permission for “see audit + anomalies”).
- Optional later matrix keys (only if product wants split control):
  - `dashboard_manage_activity_anomalies` — configure thresholds / dismiss /
    mark reviewed (if not added in v1, Power Admin / hub-admin style roles
    that already have view may dismiss via a simple “reviewed” action).
- Does NOT require the `security_monitoring` Functionality flag to view
  activity anomalies. When an anomaly is escalated into 6F, that path still
  requires Security Monitoring ON + relevant `secmon_*` caps.

Data model (suggested)
- Table e.g. `activity_anomalies` (per hub), or reuse a typed row with:
  - `id`, `hub_id`, `detected_at`, `window_start`, `window_end`
  - `anomaly_type` (machine key, e.g. `auth.new_ip_login`, `admin.action_burst`)
  - `severity` (info | low | medium | high)
  - `title`, `description` (plain language)
  - `status` (open | reviewed | dismissed | escalated)
  - `actor_user_id` / denormalised name/email/role when known
  - `source_ip`, sample `activity_log` ids in `related_activity_log_ids` (JSON)
  - `baseline` / `observed` metrics in `properties` (JSON)
  - Optional `security_event_id` / `security_incident_id` when escalated to 6F
- Sensitive payloads follow the same redaction rules as activity_logs.
- GDPR: scrub actor PII on erasure; retention via GDPR_RETENTION_* or a
  dedicated activity-anomaly retention key (align with activity_logs days).

UI (frontend — both repos)
- Activity Logs page gains a tab or sibling view **Anomalies** (or a clear
  “Anomaly detection” section) in addition to the existing feed + report.
- Anomaly list: newest-first; filters by type, severity, status, date, user/IP.
- Detail: when detected, pattern explanation, related activity-log rows
  (deep-link into existing feed), mark reviewed / dismiss; optional
  “Escalate to Security Monitoring” when 6F is enabled.
- Empty/healthy state: last detection run time + “No open anomalies”.

APIs (hub_can:dashboard_view_activity_logs unless manage key added)

  - PATCH /api/…/activity-logs/anomalies/{id}   (status reviewed/dismissed)

  (+ /power-admin/… mirrors when acting)
- Activity log mutations for settings / escalate:
  `activity.anomaly_settings_update`, `activity.anomaly_escalate`,
  `activity.anomaly_reviewed` (as applicable).

Detection cadence
- Prefer near-real-time hooks after activity_log writes for threshold rules,

- Do not invent a second “Monitor now” dependency scanner here — that stays

    everyone must sign in again under the new policy.
- Force-logout of the viewer’s own account ends their session immediately.
- Mutations are written to activity_logs (`auth.force_logout`,
  `auth.session_timeout_updated`).
- APIs (hub_can:dashboard_manage_active_sessions):

6E.3 Breach runbook (ops checklist — not a product feature)
--------------------------------------------------------------------------------
1. Detect & contain the incident (revoke access, rotate secrets, isolate).
   Prefer Security Monitoring (6F) for detection evidence when enabled.
2. Assess personal-data risk (what data, how many people, harm likelihood).
3. If notification required, report to the ICO without undue delay and within
   72 hours of becoming aware: https://ico.org.uk/for-organisations/report-a-breach/
4. If high risk to individuals, inform them without undue delay.
5. Record the technical security event/incident in Security Monitoring (6F)
   when the functionality is on. Track legal/ops GDPR follow-up in Support
   Tickets (or your ops tracker) — do not invent a second GDPR-only queue.
6. Handle related SARs / erasure via GDPR / data requests.
7. Review lessons learned; confirm processor DPAs remain current.

6F. SECURITY MONITORING MODULE (REGULAR MONITORING + INCIDENT REPORTS)
--------------------------------------------------------------------------------

Purpose
- Provide **regular, detailed security monitoring** on each hub so capable

- This is a **separate module/feature** from Activity logging / Activity Logs
  anomaly detection (6A), Compliance audit trail (6C), and Support Tickets.
  It answers security questions (threats, security incidents, dependency
  scan status), not general product usage. Activity-pattern anomalies that
  are not (yet) security incidents belong in 6A.2; escalate into this module
  when security-relevant and `security_monitoring` is ON.

Enablement
- Hub Functionalities flag: `security_monitoring` (default OFF).
- NOT a Modules-page billable packaging module (the 6 product modules stay
  unchanged). Optional future catalogue pricing is out of scope unless
  explicitly added later.
- Available on Central Hub, Shared hubs, and White-label hubs (per-hub flag).
- While off: `secmon_*` capabilities are blurred / unavailable; nav hidden;
  APIs return 403 / feature-disabled.

Who can see what (Capabilities — Hub operations group)
- `secmon_view_events` — open Security Monitoring → Events feed + detail
- `secmon_view_report` — open Security Monitoring → Report (aggregates)
- `secmon_manage_incidents` — acknowledge / investigate / resolve / close;
  add investigation notes; link related activity-log rows
- `secmon_manage_alerts` — configure thresholds, channels, recipients
- `secmon_manage_disaster_recovery` — recognize disasters for an affected
  product module; create module snapshots; roll back that module only
  (section 6B.1 — NOT whole-hub restore; NOT the same as closing an incident)
- `secmon_manage_access` — open Access Control (hub + user geo/IP/VPN rules,
  Monitor/Enforce, Simulate, History restore, emergency unlock). See
  NFR-SEC-FW section 9.5 D). Blurred while Functionalities → Security
  Monitoring is OFF.
- Defaults: ON for hub-admin style roles (power_admin when acting, 
  finproms_admin, client_admin, manager); OFF for approver / advisor /
  admin-staff / user until Power Admin enables them.
- Power Admin toggles these per hub / role on the Capabilities matrix
  (Central Hub). Only users with the relevant capability see the UI.

What is monitored (detailed event catalogue)
Each recorded item is a **security event**. Related events may be rolled into
a **security incident** for investigation. Minimum event types:

  A) Authentication & access
     - Failed login (wrong password / OTP)
     - Blocked login (suspended / discontinued / invite-only / unverified)
     - Brute-force / repeated failures threshold crossed (same IP or user)
     - Force-logout by admin; mass session revocation
     - Password reset requested abnormally often
     - Privilege / role change on a user (especially elevation)

  B) Authorization & API abuse
     - HTTP 401 / 403 spikes on protected routes
     - Rate-limit trips (`auth`, `imports`, `wc-publish`, others)
     - Access denied to Security Monitoring / GDPR / Capabilities / secrets

  C) Data & secrets
     - Attempts to read or mutate encrypted secrets (Stripe, hub DB, cPanel)
       when rejected or suspicious
     - Unusual export volume (GDPR export, hub backup download, advisor Excel)
     - Upload of disallowed / suspicious file types (NFR-SEC-FW upload scan)
     - Malware detected in upload / malware scan failure (when ClamAV enabled)
     - Application firewall IP denied / temporary auto-block (NFR-SEC-FW)
     - Access restriction block / would-block (`fw.access_restricted`,
       `fw.access_would_block`) when hub/user geo/IP/VPN rules match
       (NFR-SEC-FW 9.5 D)
     - Access policy change (`fw.access_policy_changed`) — who changed hub
       or user access rules, with before/after field diff
     - Emergency access unlock (`fw.access_emergency_unlock`)

  D) Platform / dependency health (ops-facing, still shown in the module)
     - Last successful dependency vulnerability scan result (composer audit /
       npm audit / CI) — pass / fail / overdue
     - Security hardening check reminders (e.g. SESSION_ENCRYPT, HTTPS,
       TLS verify) when detectable from config
     - Scheduler / monitoring heartbeat missed (optional)

  E) Manual / declared incidents
     - Capable user declares “Security incident” (title, description, severity)
       when something was found outside automated detectors

Event / incident record fields (report detail — REQUIRED)
  - `id`, `hub_id` / hub slug
  - `occurred_at` (precise timestamp, timezone displayed in UI)
  - `detected_at` (when the system recorded it)
  - `category` (auth | authorization | data | dependency | manual | other)
  - `event_type` (machine key, e.g. `auth.failed_login_threshold`)
  - `severity` (info | low | medium | high | critical)
  - `title` (human short summary)
  - `description` (what happened — detailed, plain language)
  - `status` (open | acknowledged | investigating | resolved | closed |
    false_positive)
  - `actor` (user id/name/email/role when known; else “anonymous / unknown”)
  - `source_ip`, `user_agent` (when available; redacted per GDPR retention)
  - `route` / `action` / request id (when API-related)
  - `related_refs` (activity_log ids, support_ticket id, user id, etc.)
  - `investigation_notes[]` (author, timestamp, note) — manage_incidents only
  - `resolved_at`, `resolved_by`, `resolution_summary`
- Sensitive values (passwords, tokens, raw secrets, card data) are NEVER stored
  in security event payloads — redact / truncate like activity_logs.

- Activity logs for mutations: `secmon.incident_declare` /
  `secmon.incident_update` / `secmon.alert_settings_update`

Detection & cadence (regular monitoring)
- Automated detectors write events as they happen (middleware / auth hooks /
  rate-limiter listeners / artisan commands).
- No daily scheduler for Security Monitoring — auth / rate-limit / force-logout
  events are recorded continuously in real time.
- Capable users run an on-demand check via POST …/security-monitoring/scan-now
  (“Monitor now” in the UI) or optionally `php artisan security:monitor`.
  That refreshes the dependency-scan summary on the Report tab.
- Optional alerts (email / existing notification channel) when severity ≥ high
  or when an incident is declared — gated by `secmon_manage_alerts`.

Retention & GDPR
- Security events support legitimate interests / security (see 6E).
- Configurable retention in `config/gdpr.php` (or `config/security_monitoring.php`)
  with prune job; anonymise actor PII on GDPR erasure while keeping event
  rows needed for security accountability (same pattern as compliance trail).
- Do not use this module as a substitute for ICO notification — see 6E.3.

Out of scope for v1 of this module
- Full SIEM / IDS / WAF product replacement
  (application-layer IP deny + upload scanning is NFR-SEC-FW / section 9.5 —
   complementary, not a network WAF)
- Network packet capture
- Automatic exploit patching without human review
- Customer-facing public status page

7. ARCHITECTURE PRINCIPLES (DERIVED FROM REQUIREMENTS)
--------------------------------------------------------------------------------
- Single codebase for Central Hub Controller + Shared hub(s) + all White-labels.
- Three instance roles: central (control plane), shared (public/content hub),
  white_label (private client hub).
- Roles: power_admin, finproms_admin, client_admin, network_admin, firm_admin,
  website_admin, top_management, accounts_admin, auditor, manager, approver,
  admin_staff, advisor, user. Each user may hold MULTIPLE roles; effective
  capabilities = UNION of assigned roles (§2.7.1). All assigned roles are equal
  (no primary / secondary). Network Admin / Firm Admin designate Document
  Repository firm heads (§3.4) and request Website Template Library sites,
  assigning Website Admins (§3.3d). Member-firm users are firm-scoped plus
  one-way Delegated compliance access (§2.7.0a). Central / Network users with
  network_admin / top_management / auditor / accounts_admin / approver may
  manage / review hub-wide (§2.7.0 B); peer / non-oversight Central staff use
  the multi-firm allowlist.
- Separate frontend shells: member catalog app (on Shared / White-label), and
  one universal Dashboard shell at /my-dashboard (tools from Capabilities +
  Power Admin pa_* checklist on Central Hub).
  Legacy /client-admin and /power-admin routes redirect to /my-dashboard.
- Tenant/hub configuration stored in database (branding, flags, rights).
- Feature flags / rights checklists must drive behaviour AND dashboard menus,
  not hard-coded forks. Power Admin has its own platform capability checklist
  (separate from per-hub checklists), stored/managed on Central Hub.
- Central Hub Controller is the configuration + remote-control source of truth
  (registry + remote DB credentials on Central; each content hub has its own DB).
- Shared Hub is a content hub only — not the control plane.
- New Shared and White-label instances are spawned by copying code to another
  cPanel and registering them on Central Hub.
- Design for future: AI generation (FinProms admin), in-app edit, compliance,
  Document Repository (Network Admin / Firm Admin + firm documents), more
  features.
- UK GDPR tooling (section 6E): privacy notice separate from Terms; DSAR
  export; anonymising erasure that preserves FCA-style audit integrity;
  retention prune jobs. Build in the phased order in 6E.1.
- Security Monitoring (section 6F / NFR-SEC): separate functionality module for
  regular security event detection and capable-user reports — distinct from
  activity logging + activity-pattern anomaly detection (6A) and the
  compliance audit trail (6C).
- Settings that vary (e.g. NEW-banner duration) come from the database.

9.4 NFR-SEC-NAV — External link / copied-URL / cross-site entry hardening
--------------------------------------------------------------------------------
Status: IMPLEMENTED (2026-10-14) — frontend guard + error page; backend
allowlist config, SafeFrontendRedirect helper, optional secmon report API.
Product choice: SHOW ERROR — do not open the target page when entry is from
paste / email / chat / redirect from another (non-hub) app.
Cross-refs: SECURITY HARDENING phase 2 (Sanctum SPA cookies + CSRF), session
SameSite, section 6F (optional security events).

Problem statement (product ask)
- Each authenticated page has a shareable / bookmarkable URL.
- If a user is already logged in and then:
    (a) copies a hub URL from somewhere else and pastes it into the browser, or
    (b) clicks a link to our application from an email / chat / third-party site
        (including phishing emails that use a *real* hub URL), or
    (c) arrives via a redirected URL that lands on our application from
        somewhere else,
  the browser may open that page while the existing session is still active.
- Product goal: **in-app navigation** (living inside the application and moving
  page-to-page via menus / in-app links / SPA router) SHALL continue to work
  normally; **external entry** via pasted URL, email link, or cross-site
  redirect SHALL NOT silently open the target authenticated page with the
  existing session.

When this IS a security risk (threat model)
  R1) Cross-site request forgery (CSRF) — attacker site or email-triggered
      navigation causes a *state-changing* action while the user is logged in
      (especially unsafe if any sensitive action is a GET without CSRF).
      Mitigated today for API mutations by Sanctum SPA CSRF + same-origin
      cookie auth (SECURITY HARDENING phase 2). Residual risk if any
      privileged GET endpoints mutate state.
  R2) Session riding / forced navigation — user is logged in; attacker tricks
      them into opening a real hub URL (phishing email with legitimate link).
      Page content may be visible without a fresh login; attacker may combine
      this with social engineering (“confirm this approval”).
  R3) Open redirect abuse — our app redirects to an attacker URL after login
      or after a flow (credential phishing). Separate control: allowlist
      redirect targets; never trust raw `?redirect=` / `?next=` from outside.
  R4) Tab / shared-device exposure — pasted deep links reopen sensitive screens
      on a shared browser that still has a live session.
  R5) NOT the same as classic phishing of a *fake* login page on another
      domain — that is user education + brand URL clarity + optional 2FA.
      NFR-SEC-NAV does not stop fake sites; it hardens entry into *our* app.

When this is NOT (by itself) a high risk
  - Opening a read-only page via a real URL while cookies are valid is normal
    browser behaviour if mutations require POST + CSRF and authorisation.
  - Password-reset, email-verification, Stripe return, and invite links MUST
    remain reachable from email without being blocked by this NFR (allowlist).

Product rule (desired behaviour)
  - ALLOW: authenticated user already inside the hub SPA; clicks in-app nav /
    router links / breadcrumbs; relative same-origin transitions.
  - ALLOW: home `/` from outside for everyone (tab search / address-bar
    of the site URL, paste, email). Authenticated users get navigation
    continuity so they can continue inside the app.
  - GUESTS on protected routes via external entry: redirect to `/login`
    (do NOT show the security ERROR — they are not authenticated yet).
  - BLOCK (authenticated): first entry into a protected route when the
    navigation context is external, including paste into a new tab,
    address-bar of a deep URL, email / chat / other-app redirect.
    Show security ERROR (do not open the target; do not silently redirect
    to home/dashboard).
  - On BLOCK (authenticated only): do NOT render the sensitive target page.
    CHOSEN UX = ERROR:
      D) Error page (SELECTED) — show a clear security error, e.g.
         “This page cannot be opened from an external link, email, chat,
         or another application. Please open the Hub from the official
         login / dashboard and navigate inside the application.”
         Do not mount the requested protected view. Provide a safe button
         to go home (or dashboard when the hub has no home page). Optional:
         auto-log the attempt when Security Monitoring is ON.
      (Alternatives kept for reference only — not selected:)
      A) Soft gate — “Continue into Hub?” interstitial then allow deep link.
      B) Re-auth — require password and/or login OTP again, then continue.
      C) Strip deep link — ignore path; send user to `/my-dashboard` silently.

Recommended technical approach (implement in BOTH repos when approved)
  Backend (hub-finproms-backend)
  1) Keep / strengthen cookie posture:
     - Prefer `SESSION_SAME_SITE=strict` (or Sanctum-equivalent) so browsers
       do NOT send session cookies on cross-site top-level navigations from
       email/other sites. Same-site in-app use still works.
     - Keep `httpOnly`, `secure` (HTTPS), Sanctum CSRF for state-changing APIs.
  2) Never rely on Referer alone (browsers strip it); treat missing Referer
     as untrusted for *entry policy*, not as proof of legitimacy.
  3) Allowlist external-entry paths that MUST work from email / payment
     providers: email verify, password reset, Stripe success/cancel, invite
     accept, public marketing pages (if any). Document the allowlist in
     config (e.g. `config/security_navigation.php`).
  4) Optional: record Security Monitoring events when external entry is
     blocked / stepped-up (`nav.external_entry_blocked`) when `security_monitoring`
     is ON (section 6F).
  5) Open-redirect hardening: validate post-login / return URLs against hub
     `frontend_url` allowlist only.

  Frontend (hub-finproms-frontend)
  1) Maintain an in-app “navigation continuity” marker (e.g. sessionStorage
     flag set after successful login / OTP and refreshed on in-app router
     transitions). Cleared when the tab/session ends.
  2) Router guard on protected routes: if the user is not authenticated →
     redirect to `/login` (never show the security ERROR to guests). If
     authenticated and continuity marker is absent OR entry looks external
     (referrer from email/chat/other app, paste into address bar / new tab,
     redirect from non-hub origin) → show the NFR-SEC-NAV error page
     (mode D); do not mount the target view.
  3) In-app `<Link>` / router.push always sets continuity; hard refresh may
     keep marker (sessionStorage) so F5 inside the app still works — product
     may optionally treat hard refresh as step-up (stricter).
  4) Do not store auth tokens in localStorage (already: Sanctum cookies).

Acceptance criteria (for “done” — when implementation is approved)
  [x] Documented product choice: mode D — show ERROR page (2026-10-14)
  [x] In-app menu / SPA navigation between authenticated pages works unchanged

  [x] Paste of a protected deep URL while logged in shows the security ERROR

9.5 NFR-SEC-FW — Firewall and malware protection

  on shared hosting (cPanel), without requiring a commercial WAF appliance
  inside the application repo.

  restrictions (country / city / IP / VPN signals) evaluated on API requests,

Product fulfilment (in-app / API)
  A) Application firewall
     - Deny list of client IPs (CIDR and/or hyphen ranges
       e.g. 203.0.113.10-203.0.113.50) configured via
       SECURITY_FIREWALL_DENIED_IPS / config/security_firewall.php.
     - Middleware DenyBlockedIps on the API group returns HTTP 403 for denied
       clients before controllers run.
     - Optional temporary auto-block of an IP when Security Monitoring’s
       failed-login threshold is crossed (SECURITY_FIREWALL_AUTO_BLOCK=true).
     - Denied / auto-blocked attempts MAY record Security Monitoring events
       (`fw.ip_denied`, `fw.ip_auto_blocked`) when the module is ON.
  B) Malware / upload protection
     - Middleware ScanUploadedFiles inspects every multipart upload on the API.
     - Reject dangerous extensions (PHP webshells, executables, scripts, etc.)
       and filenames that embed those extensions (e.g. invoice.php.jpg).
     - Reject SVG uploads by default (scriptable); favicon validation no longer
       allows svg.
     - Optional ClamAV: when MALWARE_SCAN_ENABLED=true and `clamscan` (or
       MALWARE_SCAN_BINARY) is available, scan file bytes; infected → reject
       and record `data.malware_detected` (incident). If scanner missing:
       refuse only when MALWARE_SCAN_REQUIRED=true; otherwise log and allow
       (cPanel-friendly default).
     - Rejected uploads record `data.upload_rejected` (or scan-failure types)
       when Security Monitoring is enabled.
  C) Existing complementary controls remain in force
     - HTTP security headers (SecurityHeaders middleware)
     - Rate limiters (auth / imports / wc-publish) + secmon rate-limit events
     - Per-route mime allowlists on major upload endpoints
  D) Access restrictions (Option B — Access Control)
     Practical subset of Access Control.docx (not full GLOBAL AND/deny-wins
     platform). Requires Functionalities → Security Monitoring ON + capability
     `secmon_manage_access`.
     - UI: `/my-dashboard/access-control` (Hub rules | User rules | Simulate |
       History). Removed from Security Monitoring as a nested tab.
     - Hub-wide rules apply to every API request; optional per-user rules merge
       after the caller is identified (Sanctum user / bearer token).
     - Rule gates (Option B precedence): Restrict IPs → Allow IPs → Block VPN →
       Restricted countries/cities → Allowed countries/cities → Specific UK
       cities → UK only.
     - Restrict/Allow IP entries accept: single IPv4/IPv6, CIDR
       (`198.51.100.0/24`), or inclusive hyphen range
       (`203.0.113.10-203.0.113.50`; spaces around `-` OK). Start must be
       ≤ end; same address family. Matching is binary inclusive.
     - Restricted / Allowed countries/cities: each gate has country codes +
       city names. Specific UK cities remains a separate UK-only allowlist.
     - Opposing lists must not overlap (UI alerts + API 422): Restricted IPs
       vs Allowed IPs (incl. CIDR/range overlap); Restricted vs Allowed
       countries; Restricted vs Allowed cities; GB cannot be Restricted while
       UK only / Specific UK cities is enabled.
     - Blocked attempts are logged as security_events (`fw.access_restricted` /
       `fw.access_would_block` / `fw.ip_denied`) with user, country, city, IP,
       path, and rule — NOT activity_logs and NOT Change history. Access Control
       UI tab “Blocked attempts” lists them (`GET …/access-control/blocked-attempts`).
     - 403 responses include `code` + hub `branding` so the SPA shows logo +
       loader (AccessBlockedSplash) without revealing deny details.
     - Block VPN: best-effort detection (edge `X-App-Geo-Vpn` and/or ip-api
       proxy/hosting). Allow IPs can override.
     - Enforcement mode per hub/user settings: **Monitor** (evaluate + log
       `fw.access_would_block`, allow) or **Enforce** (HTTP 403 +
       `fw.access_restricted`). If both hub and user modes are active,
       Enforce wins.
     - Simulate: dry-run same decision engine for an IP (+ optional user /
       country / city / VPN overrides). Never blocks; never writes deny events.
     - History: `fw.access_policy_changed` with field-level before/after;
       restore previous (“before”) or “after” snapshot via API.
     - Lockout recovery: save confirms when Enforce would block the actor’s
       current IP (409 `self_lockout_risk` unless acknowledged); Emergency
       unlock / Switch to Monitor in UI; CLI `php artisan access-control:unlock`;
       authenticated users with `secmon_manage_access` are soft-escaped from
       hard 403 (logged as would-block) when ACCESS_RESTRICTION_ADMIN_ESCAPE
       is true (default).
     - Trusted request data (architecture § Trusted request data):
       - TRUSTED_PROXIES — Laravel trusts X-Forwarded-* only from listed
         proxies (empty = ignore forwarding headers). Use `*` only when origin
         is firewalled so clients cannot hit Laravel directly.
       - GEOIP_TRUST_HEADERS / GEOIP_REQUIRE_TRUSTED_PROXY_FOR_HEADERS —
         CF-IP* / X-App-Geo-* used only from a trusted proxy (or Simulate
         force-trust). Generic X-Country-Code / X-City off by default.
       - Per-deploy `.env` (each hub server), not stored in Access Control UI.

Operational fulfilment (infra — outside Laravel code)
- Operators SHALL keep the host firewall / fail2ban / provider WAF (if any)
  enabled for the public IP and SSH; document in ops runbook.
- Where ClamAV is required by policy, install and update virus definitions on
  the server, then set MALWARE_SCAN_ENABLED=true (and REQUIRED if fail-closed
  is mandated).
- For Access Control in production behind Cloudflare/LB: configure
  TRUSTED_PROXIES appropriately and keep origin locked to the edge; enable
  GEOIP_REQUIRE_TRUSTED_PROXY_FOR_HEADERS so forged geo headers on a direct
  origin hit are ignored. Run pending access-restriction migrations on each
  hub database.

Out of scope / explicit non-goals
- Replacing a full network WAF / IDS / SIEM product (already out of scope in 6F)
- Guaranteeing zero malware without host AV + patched OS
- Scanning files already stored on disk from before this NFR (no retroactive
  bulk re-scan job in v1)
- Frontend-only changes (backend enforces uploads; SPA needs no gate)
- Full Access Control.docx platform in v1: GLOBAL scope AND-combine across

  city confidence thresholds, webhook/service policies, live WebSocket
  re-evaluation (documented architecture; not shipped as Option B)

9.6 NFR-SEC-APP — Protection against SQLi, XSS, CSRF, brute-force, malware, DDoS
--------------------------------------------------------------------------------
Status: IMPLEMENTED (2026-10-14) — formalises existing hardening + closes gaps
(SafeHtml on save, global API throttle, stronger auth throttle keys).
Volumetric / network DDoS remains an ops / CDN / host-firewall duty — Laravel
rate limits are application-layer abuse mitigation only.

Statement
- The platform SHALL protect against SQL injection, cross-site scripting (XSS),
  cross-site request forgery (CSRF), brute-force authentication attacks,
  malware in uploads, and server-side request forgery (SSRF) on trusted
  outbound HTTP (WC embed / cPanel / preview), and SHALL apply application-
  layer throttling against abusive / flood traffic. Network-layer DDoS
  absorption (CDN, provider WAF, host firewall) SHALL be maintained
  operationally outside this codebase.

Product fulfilment

  A) SQL injection
     - All user-influenced queries use Eloquent / query builder parameter
       binding. Raw SQL (`whereRaw` / `orderByRaw` / `selectRaw`) MUST use
       placeholders or static fragments only — no string concatenation of
       request input into SQL.
     - Validation of inputs before persistence remains mandatory.

  B) XSS (cross-site scripting)
     - API JSON responses carry restrictive CSP via SecurityHeaders
       (`default-src 'none'` for non-document APIs).
     - Stored rich HTML (Terms / Privacy / Cookie notice) is sanitized on
       save with `App\Support\SafeHtml` (allowlist; strips script / handlers /
       javascript: URLs) when SECURITY_SANITIZE_RICH_HTML=true.
     - SPA uses DOMPurify (`sanitizeRichText`) before `dangerouslySetInnerHTML`
       (CookieBanner + RichTextDisplay). Frontend remains the primary render
       gate for HTML pages.
     - Scriptable uploads (SVG, PHP, etc.) blocked by NFR-SEC-FW.

  C) CSRF
     - Sanctum SPA stateful cookies + CSRF (`statefulApi`, ValidateCsrfToken)
       for mutating API calls from the first-party frontend (SECURITY
       HARDENING phase 2). CORS credentials allowlist FRONTEND_URL.
     - Bearer personal-access tokens (if used) are not CSRF-vulnerable the
       same way; cookie SPA is the primary browser auth mode.
     - NFR-SEC-NAV reduces session-riding via external deep links.

  D) Brute-force
     - Named limiter `auth` (SECURITY_AUTH_RATE_PER_MINUTE, default 20/min)
       keyed by IP and email when present; applied to login / register /
       password reset / OTP routes.
     - Login OTP attempt caps + resend throttle; password-reset broker throttle.
     - Security Monitoring records failed logins and escalates on threshold;
       optional SECURITY_FIREWALL_AUTO_BLOCK temporary IP deny (NFR-SEC-FW).

  E) Malware
     - Delivered by NFR-SEC-FW (section 9.5): upload scan middleware, dangerous
       extension / SVG rejection, optional ClamAV.

  F) DDoS / flood abuse (application layer)
     - Global named limiter `api` (SECURITY_API_RATE_PER_MINUTE, default 120/min
       per user or IP) via `throttleApi('api')`.
     - Additional tighter limiters: `imports`, `wc-publish`, `auth`.
     - Stripe webhook excluded from global throttle (burst deliveries).
     - Rate-limit trips may record `api.rate_limited` in Security Monitoring.
     - NOT a substitute for CDN / cloud DDoS protection or host firewall.

  G) SSRF (server-side request forgery) — WC outbound
     - Public embed proxy (`/api/website-compliance/embed-site/...`) and
       cPanel sync posts MUST call `SafeOutboundUrl` before any server-side
       HTTP fetch. Block loopback, RFC1918, link-local, and cloud metadata
       hosts (e.g. 169.254.169.254); do not follow redirects off-host.
     - `cpanel_domain` on deploy / promote-to-live is validated on write
       (literal private/metadata hosts rejected). Fetch paths also resolve
       DNS and fail closed on private answers.
     - Template preview capture already used the same helper; embed + cPanel
       must stay aligned.
     - Hub-scoped embed (`/embed-site/h/{hubId}/` or `?hub_id=`) MUST
       authorize before `WhiteLabelDatabaseService` runs: Sanctum session or
       `embed_ticket` from POST `/api/website-compliance/embed-ticket`
       (`WcEmbedTicket`). Anonymous remote DB opens are forbidden.

  H) Hub machine callbacks — purpose-scoped secrets
     - `/api/internal/*` MUST NOT share one master key across backup, restore,
       GC file bridge, and deploy-env. Each purpose has its own header +
       per-hub token + optional shared env fallback (`HubInternalAuth`).
     - Optional `HUB_INTERNAL_ALLOWED_IPS`; dedicated rate limiters
       `internal-hub` and `internal-restore`.

Operational fulfilment (out of app code)
- Keep cPanel / host firewall, fail2ban (or equivalent), TLS, and optional
  CDN/WAF in front of public hosts.
- Patch OS and run dependency audits (NFR-SEC CI still optional).
- Install ClamAV on the server if malware fail-closed policy is required.

9.7 NFR-BACKUP-ENC — Hub backup encryption at rest
--------------------------------------------------------------------------------
Status: IMPLEMENTED (2026-10-14). Detail lives with section 6B; this NFR is the
security statement for encrypted archives.

Statement
- Hub backup ZIP archives SHALL be encrypted at rest on disk so a filesystem
  copy / hosting compromise does not expose plaintext SQL dumps and uploaded
  files. Download and restore SHALL decrypt transparently for authorised
  operators when the correct key is configured.

Mechanism
- Streaming AES-256-GCM with magic header `HBENC1` (`HubBackupEncryptedArchive`).
- Config: `HUB_BACKUP_ENCRYPT_AT_REST`, `HUB_BACKUP_ENCRYPTION_KEY` (shared).
- Create → zip → encrypt in place; receive/mirror preserve ciphertext;
  restore/download decrypt to temp ZIP.
- Column `hub_backups.is_encrypted`; legacy plaintext still supported.

Ops
- Generate one key; set identically on Central + all content hubs.
- Rotate by setting a new key only after old archives are pruned/expired, or
  keep the old key available until retention clears ciphertext encrypted with it
  (v1 has no multi-key ring — rotate carefully).
- Protect the key like APP_KEY; never commit it.

Acceptance criteria
  [x] New backups encrypted when encrypt_at_rest enabled + key available
  [x] Download streams plaintext ZIP to Power Admin
  [x] Restore works for encrypted and legacy plaintext archives
  [x] Dual-store upload passes is_encrypted; Central does not double-encrypt
  [x] Documented in §6B + §8 + this subsection; tests cover round-trip

Related but distinct
- NFR-GC-ENC — Generic Compliance field/file crypto (not backups)
- NFR-AVAIL / §6B / §6B.1 / §9.9 — schedule, dual store, retention, DR/rollback
- NFR-PRIV — erasure does not rewrite historical backup dumps
- NFR-SEC-VAL (9.8) — request validation/sanitization (not archive crypto)

9.8 NFR-SEC-VAL — Server-side validation and sanitization of all user inputs
--------------------------------------------------------------------------------
Status: IMPLEMENTED (2026-10-15) — formalises mandatory Laravel validation on
mutating APIs + global wire scrub + field-type sanitization for stored content.
Complements NFR-SEC-APP (XSS) and NFR-SEC-FW (upload malware); does not replace
them.

Statement
- The platform SHALL validate all user-supplied inputs on the server before
  business logic persists or acts on them, and SHALL sanitize those inputs to
  remove dangerous control characters and, for rich-text fields, disallowed
  HTML. Client-side checks MAY improve UX but MUST NOT be trusted as the only
  gate.

Product fulfilment

  A) Validation (every mutating API)
     - POST / PUT / PATCH (and body-bearing DELETE) endpoints SHALL call
       `$request->validate([...])` (or an equivalent private helper that does)
       and return HTTP 422 with structured errors on failure.
     - Rules MUST enforce type, length/max, allowlists (`Rule::in` / `exists`),
       and file `mimes`/`max` where applicable.
     - Machine/internal endpoints (hub backup bridge, Stripe webhook) SHALL
       still authenticate (shared secret / signature) and validate file or
       payload shape before use.
     - Query filters on list endpoints SHOULD be validated or cast to safe
       types (`integer()`, allowlisted enums) — never concatenated into SQL.

  B) Sanitization (defence in depth)
     - Global API middleware `SanitizeRequestInput` (config
       `SECURITY_SANITIZE_REQUEST_INPUT`, default true) strips null bytes and
       C0 control characters (except tab/LF/CR) from every request string
       before controllers run. Laravel’s built-in TrimStrings /
       ConvertEmptyStringsToNull remain enabled.
     - Plain-text fields (names, subjects, email template copy, etc.) use
       `InputSanitizer::plain()` — strip tags + trim.
     - Stored rich HTML (Terms / Privacy / Cookie notice, GC/SMC description
       & feedback, support ticket description/comments, WC section /
       change-request content, post/bundle descriptions) use
       `InputSanitizer::richHtml()` → `SafeHtml` allowlist when
       `SECURITY_SANITIZE_RICH_HTML=true`.
     - Structured settings payloads continue to use key allowlists
       (e.g. `PageContentDefaults::sanitize`).
     - Paths / redirects use `SafeFrontendRedirect` (NFR-SEC-NAV).
     - Uploads remain gated by NFR-SEC-FW (`ScanUploadedFiles`).

  C) Frontend (complementary, not sufficient alone)
     - SPA uses `sanitizeRichText` (DOMPurify) before `dangerouslySetInnerHTML`
       and SHOULD sanitize rich-text payloads on submit before calling the API.
     - Form-level required/format checks remain for UX; server returns 422.
